状态：定稿。机器 192.168.1.98（1 主卡 P100-12G = CUDA0，3 张 P104-8G helper = CUDA1/2/3），

## 0. 结论（最重要，先说）

**最优 bench 配置（pp512/tg128，3 helper 行切分，稳态取 bench 2）：**

```
STRATA_REMOTE_ZEROCOPY=0 STRATA_Q36_HELPER_ASYNC=1 STRATA_Q36_HELPER_PARALLEL=1 \
STRATA_Q36_FIXED_SLOTS=1 STRATA_Q8_SM60=1 \
./bin/strata-q36 --model /home/models/Qwen3.6-35B-A3B-UD-Q4_K_XL.gguf \
  --expert-cache-device1 auto --expert-cache-device2 auto --expert-cache-device3 auto \
  --kv int8 --max-context 2048 --no-warmup
```

**一句话结论**：3 helper 行切分 + ZC=0 + ASYNC + FIXED_SLOTS + P100 专用 `Q8_SM60` 在 fp32 下把
bench 2 tg128 从 47.7 提到 51.2（+7.3%），叠加 `--kv int8` 到 **52.5（+10.1%）**，pp512 ~158 不变；
MTP 的甜点位在 **`--mtp 3`**（`--tokens` 路径 66.2–67.2 tok/s，比纯 decode 49.3 快 **+34~36%**），
盈亏线在 D=0 与 D=1 之间（本机连 1 条草稿都赚），`--mtp-adaptive` 在线学习在随机 prompt 上锁 D=3、
重复 prompt 上锁 D=4；整轮默认路径 `gen: 220` 逐字节门保住，int8 路径自洽（两次同配一致）。

增益来源排序（MEASURED）：
1. **3 张 helper 全开（行切分）**：1 卡 28.4 / 2 卡 37.4 / 3 卡 47.8 —— 数量是第一变量；
2. **`STRATA_REMOTE_ZEROCOPY=0` + `STRATA_Q36_HELPER_ASYNC=1`**：Ornith 轮实测 +65% 的那条路，
   本模型上同样必开（ASYNC 关 tg 掉到 43.8）；
3. **`--kv int8`**：本轮唯一的 bench 实质增益（47.7 → 49.3，+3.4%），代价是 token 流分叉
   （opt-in 语义，验收「自身确定」）；
4. **`STRATA_Q8_SM60=1`**（origin/main `6e29a5d3`，P100 专用 Q8_0 解码 GEMV）：+5.3%（fp32 门
   bit-exact）/ +6.3%（叠 int8）；
5. **`STRATA_Q36_FIXED_SLOTS=1`**：+0.1，小但稳，已纳入；
6. **MTP（`--mtp 3`）**：decode 路径再 +34~36%，但 **`--bench-tg` 看不到**（bench 从不跑
   spec_step，见 §3.0）。

### 2.3 明显更差 / 别再试（MEASURED，按损失排序）

1. **层切分（`PARALLEL` 关）**：tg128 29.1（2026-10-20 第二轮 h3.log 同值）——务必 `PARALLEL=1`。
2. **只用 1 个 helper**：tg128 28.4；2 个 37.4；必须 3 个。
3. **ASYNC 关**：43.8，必开。
4. **显式 `--expert-cache-deviceN 2000`**（第二轮的坑，仍在）：限死专家数 → 29.5；auto 才 47.7+。
5. **ZC=1**、**expert-slots 64**：VRAM 不足直接崩。
6. **`--max-context 512`**：`:3327` IMA（auto chunk 2048 越过 512 格 KV），真实 bug，ctx 别用 <1024
   （1024 实测与 2048 持平，可用但无收益）。
7. **MTP1 在 bench 里「不推荐」的旧判断已被 §3 修正**：tg 持平是 bench 不跑 spec_step 的假象，
   pp 掉 4.6 是真的；decode 重的负载 D=3 净赚，见 §3.2。
8. **PEERS、expert-vram/expert-slots 微调、k8v32/k32v8**：中性或更差，白做（k8v32 48.2 比 int8 49.3 差）。

### 2.4 崩溃清单（别再当性能问题查）

- `--max-context 512` → `q36_engine.cu:3327` 非法内存访问，重复 4 次；根因（DERIVED）：auto chunk
  256..4096 选了 2048，越过 512 格 KV。ctx ≥ 1024 无此现象。
- `ZC=1` → VRAM 剩 0.89G 装不下 zero-copy 映射，启动即崩。
- `--expert-slots 64` → 需 6054 专家/层 × 40 层，剩 5186，VRAM 不足。

### 2.5 没测 / 没拿到干净值的（明说）

- **`--chunk 1024`（强压）**：被抢卡反复杀，没拿到干净值。DERIVED：auto 已选 2048 且
  `docs/QWEN36.md` 定 2048 最快，强压 1024 只会更慢，不值得重测。
- 表内每个数字是 2–3 次重试后的干净单值（噪声带参考：同配置两连跑 49.1/49.3，~0.4%）。

### 2.6 测量环境纪律（本轮实际执行情况）

每个 run 前 `pkill -9 -x strata-q36` + `free -g` avail ≥ 12G + 显存全 0（共享机规矩，§7）；

## 3. MTP：逐位接受率、盈亏线、推荐参数（全部 Qwen3.6 实测，`--tokens` 路径）

### 3.0 必须先知道的坑：`--bench-tg` 从不投机（MEASURED，本轮最重要的方法学事实）

`--bench-tg` 走 `process()` 逐 token，**从不进 `spec_step`**：最优 bench 配置下 `--mtp 0..4`
的 tg128 全部是 49.3–49.4，一条不差。所以：

- 表 2.2 里「MTP1 tg 持平」不是「MTP 没用」，是 bench 看不见 MTP；
- MTP 的任何收益/代价只能读 `--tokens` / serve 路径的墙钟；
- 反过来，`--mtp 1` 在 bench 里拖的 4.6 pp512（153.8 对 158.4）是 prompt 侧真实成本。

### 3.1 逐位（逐深度）接受率（MTP-DEPTH 默认报告，20-token prompt，n 64）

`d` = 深度，读法：该行的接受率是「前 d 条草稿全部命中」条件下的条件接受率（MEASURED，
docs/QWEN36.md 原文带 1 位小数）：

| d | 随机 id（99999, 88888…） | 1..20 升序（可预测续写） |
|---:|---:|---|
| 0 | 83.3% | 90.9%（D=1；D=2 时 87.5%） |
| 1 | 76.5% | ~87% |
| 2 | 56.2% | ~83% |
| 3 | 43.8% | ~79% |
| 4 | 31.2% | ~77% |
| 5 | 20.0% | ~73% |
| 6 | 13.3% | ~73% |

曲线随深度单调衰减；可预测续写（重复/模式）能把高接受率保持到 6–7 深。这是 Qwen3.6 的 MTP 块
（Unsloth MTP GGUF 自带）的行为——与 Ornith（Q4_0 头、nextn 块只训一步、草稿 3/4 接受 0 个）
**完全不同**，Ornith 的 MTP 结论不能搬（§6）。

### 3.2 速度与盈亏线（`--tokens` 路径，int8 KV + FIXED_SLOTS + 3 helper，无 Q8_SM60）

| `--mtp` D | tok/s | vs D=0（49.3） |
|---:|---:|---|
| 0（纯 decode） | 49.3 | 基线 |
| 1 | 56.4 | +14% |
| 2 | 61.4 | +24% |
| **3** | **66.2–67.2** | **+34~36%（最优）** |
| 4 | 60.9 | +23% |
| 5 | 61.1 | +24% |

**盈亏线在 D=0 与 D=1 之间：本机连 1 条草稿都是净赚。** 曲线先升后降，顶点 D=3——验证窗口与
草稿链的行成本随 D 线性涨，而 §3.1 的逐位接受率随 D 衰减，两者相乘在 3 处最大。
重复型 prompt 曲线更平（D=3 68.0 / D=4 67.8 / D=5 67.6）。

**推荐参数（按场景）：**
- 固定深度：`--mtp 3`（随机/一般 prompt 甜点位，+34~36%）；可预测续写可推 `--mtp 4`；
- 不预设深度：`--mtp 7 --mtp-adaptive N`（默认池 4；§3.3）；
- serve 双并发：`--batch 2 --mtp 2 --batch-mtp`（§3.4）；
- **`--draft-vocab` 保持 0（全词表）**：q36 的旗标语义是「前 N 个 token id」，实测
  0 vs 65536（`--mtp 2`，随机 id）58.5 vs 61.7 tok/s 在重复噪声内、接受总数 40/48 两边相同
  ——中性，不搬 Flash-Next 的「16K–131K 有利」结论（那是它的子集文件语义 + Q4_K_XL 实测，
  对本旗标语义不适用；DERIVED）；
- 纯 prompt 负载：`--mtp 0`（MTP 拖 pp512 4.6，§3.0）。

### 3.3 `--mtp-adaptive N`（本轮新增，opt-in，默认路径逐字节不变）

搬的是 `src/spec/draft_policy.cpp` 的**自适应停止思想**（最小搬移：per-深度 EMA 学「接受草稿数 +
步耗时」，目标量 committed tokens/ms）：每个深度探 3 轮（`kProbes`，`q36_engine.cu:1686`，
未探完的深度不被单次坏轮否决，形状同 DraftPolicy），全部探完才锁定最优深度并每轮重测；
D=0（纯步，也计时）在池内，防外推否决。报告行 `MTP-ADAPT: rounds per draft depth...`
（`:6097`）。实测：`--mtp 7 --mtp-adaptive 5` 随机 prompt 探 0–5 后**锁 D=3，65.1 tok/s**
（固定 D=3 是 66.2，差 13 轮探索成本）；重复 prompt **锁 D=4，67.2**。`--mtp 0` 路径无
MTP-ADAPT 输出、stderr 零新增字节。

没搬的及原因（本轮四条调研 + MTP 调优轮定案）：

- **SuffixDrafter / DraftSource / Controller**（`src/spec/`）：Controller 全仓无调用者，
  角色已被 DraftPolicy 取代（DERIVED）。SuffixDrafter 已于 2026-10-21 接入，
  见下方「2026-10-21 补充」；
- **Flash-Next `core/mtp.hpp` 全家**（coupled 采样 `STRATA_SPEC_COUPLED/PROB`、`--mtp-q4`
  4-bit 副本、`--mtp-hnorm`、K/V ring、`STRATA_MTP_PROFILE` 段戳、`chain_launch` 异步流水线）：
  q36 引擎**不引用** `core/mtp.hpp`，两套实现互不引用；且 q36 的 MTP 块来自模型 GGUF 本身
  （Unsloth MTP GGUF），`mtp_fetch.py/mtp_pack.py/mtp_rt.py` 三个脚本全服务 Flash-Next 的
  qwen4exp MTP，产出 q36 用不了。照搬无意义，要什么在 q36 引擎内重做。

### 3.4 `--batch-mtp`（本轮首次实测，双并发 session）

`--batch 2 --mtp 2 --batch-mtp`，int8 KV + FIXED_SLOTS：两 session 各 53.6 / 57.4 tok/s，
对纯 decode 的 48.0 / 51.9，**+10%**；每 session 文本与其 solo 文本相同（窗口 8 行，
每 slot 一条 2-draft 提案，18/26 与 20/26 接受）。上游 `docs/QWEN36.md` 的 batch-mtp 表
（1 请求 1.60× 等）是 Flash-Next 的数字，本条是 q36 首次实测。

> 2026-10-21 补：这组数字是**旧配置**（没有 `Q8_SM60`、没有固定槽）下的一次测量，且
> 脚本 `.run/bmtp_q36.sh` 用的是 `--tokens`，**走不到 `--batch-mtp`**（该路径只在 serve 多 slot 生效）。
> 推荐配置下的复测见下方「2026-10-21 补充」。

### 3.5 parity 与质量门（MTP 各路径都过）

- 默认路径（无旗标、fp32）`gen: 220 16 15 15 15 20332 1740 369`（`--tokens 32 --n 8`），
  开/关 `--mtp-adaptive`、开/关 `Q8_SM60` 各跑一次，**逐字节一致**；
- int8 路径：自洽（两次同配一致、不崩、不算错），token 流与 fp32 分叉是 int8 量化噪声
  （runbook 2026-10-18「int8 KV 的质量实测」已在上游「与 fp16 不可区分」区间内定案）；
- `--mtp-calibrate`（离线探针）与 `--mtp-adaptive`（在线 learner）判定同向；两旗标同给时
  探针的 `speculating = false` 结论仍成立（答案走纯 decode）。

## 4. 上游：有什么值得搬、搬了哪些、没搬为什么

**前提核实（MEASURED，`git merge-base --is-ancestor`）**：`origin/main` 是 HEAD（`fa104a05`）
的**祖先**——HEAD 已完整包含 origin/main 全部提交，**不存在「没用上的 origin/main 提交」**。
研究员初列的 sm_60/PCIe/prefill 开关（`STRATA_Q8_SM60`/`STRATA_PCIE_BALANCE`/
`STRATA_EXCHANGE_ROTATE`/`STRATA_KV_HOST_REGISTER`/`STRATA_HANDOFF_PIPE`/`577abb03` 流式提示
层等）在树里**全都已存在**（grep 命中）。所以「搬」的实际含义 = **把树里已有、但未在本机
实测的 opt-in 旗标在真机量出来，把赢的纳入推荐配置**。

| 项 | 判定 | 去向 |
|---|---|---|
| `STRATA_Q8_SM60=1` | **+5.3% / +6.3%，fp32 门 bit-exact** | **已采纳**进推荐配置（§0） |
| `STRATA_PCIE_BALANCE=1` | 中性（tg128 持平） | 不纳，不写进推荐 |
| `STRATA_EXCHANGE_ROTATE=1` | 中性（同上） | 不纳 |
| `STRATA_KV_HOST_REGISTER` | 只影响启动寄存器方式，非 decode 速度项，且已默认 | 不动 |
| `STRATA_HANDOFF_PIPE` 等 prefill 多卡协同 | 已在树，属 prompt 侧 | 本轮未单列实测；decode 最优配置不涉及 |

**远端功能分支 `aflin/qwen36`（`pr1402-now`）4 个提交不在 HEAD**（`42bf2ff6` qwen35moe
35B-A3B 模型支持、`20f4d4bb` 8K 16-bit KV + sub-sm_75 server 等）：

- **没搬，理由**：服务 8–12GB 小显存第二模型/低算力卡 server，对 P100 12G + 3×P104 的多卡
  decode **无增量收益**；搬入要动 `src/program/generate.cpp` 与 `remote_experts.*`（与 Flash-Next
  共享），越界且无收益。冲突面：无（4 个提交与 HEAD 树不重叠）；
- 本机若以后要跑那个小模型，再从远端分支取，不在本轮范围。

**结论**：「上游优化没用上」的担忧在当前分支不成立；本轮唯一新增采纳是 `Q8_SM60`

## 5. 四条调研的落点（摘要，全文在 2026-10-20 四条调研记录）

## 7. 操作纪律（从数字里提炼；旧 REMOTE_BOX_RULES 在 `stash@{0}^3`，不在工作树）

1. 每个 run 前 `pkill` + `free -g` avail ≥ 12G + 显存全 0（共享机规矩）；
2. 墙钟 tok/s 是唯一权威，稳态取 bench 2；`--bench-tg` 的数字**永远不带 MTP 语义**（§3.0）；
3. `--kv int8` 的验收是「自身确定」（前后两次一致），不是与 fp32 逐位；
4. `--max-context` 别用 512（IMA bug，§2.4）；
5. `--expert-cache-deviceN` 用 `auto`，别显式写数（限死专家数 = 丢 GPU 命中率，§2.3.4）；
6. helper 数能开几张开几张（1/2/3 卡 = 28.4/37.4/47.8，§2.2）。

## 2026-10-21 补充：`--suffix-draft` 接入、`--batch-mtp` 复测、Stager 否定

同机同模型，推荐配置（三张 helper `auto` + `ZEROCOPY=0` + `HELPER_ASYNC=1` +
`HELPER_PARALLEL=1` + `FIXED_SLOTS=1` + `Q8_SM60=1` + `--kv int8`）。

### `--suffix-draft N`（新开关，opt-in，默认关）

把 Flash-Next 的 `SuffixDrafter` + `DraftPolicy` 接到 q36 的 `spec_step`。
每轮在「后缀查找窗口」和「MTP 窗口」之间二选一，选中后缀窗口就不再跑 MTP 草稿链。
与 `--mtp-adaptive` 互斥。`--mtp 0` 也能用（退化为和普通解码步比）。

| 配置 | tok/s | 说明 |
|---|---|---|
| 重复 token，`--mtp 2` | 75.7 | 对照 |
| 重复 token，`--mtp 2 --suffix-draft 7` | **113.5–113.8** | **+50%**，两次同向 |
| 重复 token，`--mtp 3` | 86.5 | 对照 |
| 重复 token，`--mtp 3 --suffix-draft 7` | **113.2** | +31% |
| 随机 id，`--mtp 2` | 59.2 | 对照 |
| 随机 id，`--mtp 2 --suffix-draft 7` | 58.5 | 持平（命中不了就退回 MTP） |

生成序列开/关**逐字节相同**。关闭时三次 `gen: 220` 对照通过。

### `--batch-mtp` 复测（serve 双并发）

两个 slot 同时解码，各生成 48 个 token，3 次。`--batch-mtp` 只在 serve 多 slot 路径生效，
`--tokens` 和 `--bench-tg` 都走不到它。

| | slot 0（随机 id） | slot 1（重复 token） |
|---|---|---|
| 不开 | 1961–2050 ms，约 23.4–24.5 tok/s | 1161–1169 ms，约 41.1–41.4 tok/s |
| 开 | 1876–1934 ms，约 24.8–25.6 tok/s | 986–1005 ms，约 47.8–48.7 tok/s |
| 差 | 约 +5% | 约 +17% |

两路合计约 65 → 73 tok/s，**+12%**。三次同向。两个 slot 的 token 序列开/关逐字节相同。
草稿被用上：slot 0 接受 21/26，slot 1 接受 23/24。

注意：不开时两路只有 24 和 41 tok/s，是因为两个 slot 在抢同一张主卡和三张 helper，
不是单路的 52.5（推荐配置 bench 2 的 tg128，见 §0 `:23` 与表 `:90`；
52.7 没有 bench 行，是笔误）。§3.4 那组 48.0/51.9 → 53.6/57.4 是旧配置下的一次测量，且脚本用的
`--tokens` 走不到这条路径，**不能当现在的结论**。

### Stager 否定

把 Flash-Next 的 `Stager`（16 深 pinned ring + 多主机线程）搬进 q36 的 `stream_kick`
（2 深单拷贝流）：**没有收益，不做**。详见 `plans/2026-10-21-q36-stager-benefit-negative.md`。
原因一句话：q36 的拷贝源在加载时就已经进了 pinned 主机内存，Flash-Next 的 Stager 解决的是
从磁盘读的问题，两个东西不是同一件事。
