# V100: upstream v0.1.39 merge on fork main

## Result

The final merge-tree binary (fork main merged with upstream v0.1.39, engine self-version
0.1.39, engine SHA-256 `e9ad337a…`) raises prompt (prefill) throughput on two Tesla V100
cards at all three measured sizes versus the fork main baseline. The gains are +2.44% at
2,048 tokens, +3.93% at 8,192 tokens, and +0.94% at 32,768 tokens. Every request generated
up to 128 tokens, so decode was also measured; the outputs are not bit-identical (see
"Output parity").

| Prompt tokens | Baseline tps (median) | Final tps (median) | Change | Baseline prefill (median) | Final prefill (median) | Less time |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 2,048 | 701.41 | 718.545 | +2.44% | 2,921.8 ms | 2,851.1 ms | 2.42% |
| 8,192 | 1,402.82 | 1,457.97 | +3.93% | 5,839.85 ms | 5,618.95 ms | 3.78% |
| 32,768 | 2,262.4 | 2,283.73 | +0.94% | 14,484.3 ms | 14,348.45 ms | 0.94% |

Each value is the median of two fresh requests (repeated twice, `reused=0`). The medians
are the mean of the two measured values, because the sample is even. The change is the
difference of the tps medians divided by the baseline tps median, derived from the exact
values (2.4426%, 3.9298%, 0.9427%). Throughput = fresh prompt tokens x 1000 / prompt time,
from the engine's `DONE` record.

The gains are measured values from two repeats per size per arm, and the arms were not
interleaved: the baseline ran first and the final binary ran last. No statistical
significance is claimed. At 2,048 and 32,768 tokens the change is comparable to the
baseline's own within-arm repeat spread (5.18% and 1.26% of its median; the final arm's
own spreads are 3.54% and 0.01%); only the 8,192-token gain (3.93%) clearly exceeds both
arms' spreads (1.09% and 1.11%).

At 2,048 tokens the engine batches 2,047 prompt tokens in its first chunk (its `PP` record
shows 2,047 of 2,048; the last token is processed separately). At 32,768 tokens the prompt
runs in four chunks (8,192 / 16,384 / 24,576 / 32,767) at about 8,192 tokens per chunk.

## Release measurement (`9a82265a…`), supplementary

The build that immediately preceded the final binary ("release", engine SHA-256
`9a82265a…`) was measured with the identical harness, prompts, and settings, and reached
720.78 / 1,462.065 / 2,289.96 tok/s. The native disk-offload path is unchanged between the
release and final binaries (both prefill arms run with prompt and conversation caching
disabled; see "System and configuration"). The final-arm values are 0.3% lower at every
size — inside the repeat spread of both arms. The release run is published as the
supplementary intermediate measurement; it is *not* the final result, and its numbers must
not be quoted as if measured on the final binary. The release binary is the one
used for the failing conversation-disk regression capture and for the 512K batch-fallback
verification ("Conversation-disk restore precedence" and "512K batch fallback"), so it is
retained in full in the result directory.

## Output parity

First generated tokens (6 rows, baseline vs final `e9ad337a…`): identical in every row —
87 / 9665 / 11 / 15 / 28 / 19. Complete outputs:

- The complete output is identical only at 2,048 tokens, repeat 1 (the 17-token request
  that stopped early).
- 2,048, repeat 2: first divergence at token 32 (tokens 0-31 identical; the two outputs
  agree on 32 of 128 positions before diverging).
- 8,192: first divergence at token 12 (repeat 1) and token 19 (repeat 2).
- 32,768: first divergence at token 17 (repeat 1) and token 33 (repeat 2), and the
  stopping points differ — the baseline stopped after 43 and 111 tokens, the final binary
  generated 128 (repeat 1, full length) and 83 (repeat 2, model stop).

The two binaries account for the resident expert cache differently (baseline: 13,371
resident slots, 5,714 slots on CUDA 1, 2,486 slots borrowed for the prompt path; final:
13,214 resident slots, 5,557 on CUDA 1, 2,244 borrowed). The GPU computes the cached
experts, and it rounds differently from the CPU, so a different resident set produces a
different continuation; only the shortest output stayed identical.

The divergence positions are not stable across builds of the same merge: the release arm
(`9a82265a…`) happened to produce byte-identical outputs on three of the six rows (2,048
repeat 1, 2,048 repeat 2, and 32,768 repeat 2) and diverged at token 39 (8,192, repeat 1),
token 27 (8,192, repeat 2), and token 17 (32,768, repeat 1). This report makes no decode
or quality claim, and the 8,192 and 32,768 outputs also differ between the intermediate
candidate and the helper arm.

## Method

The harness [`bench/run_v100_prefill.py`](../bench/run_v100_prefill.py) speaks the engine's
own stdin/stdout serve protocol. It sends the token ids directly, so the engine's prompt
length equals the requested length: there is no template and no probe request. The HTTP
harness [`bench/run_v100_bench.py`](../bench/run_v100_bench.py) is not used for the prefill
arms.

Every arm recorded harness revision
`ae03df48882fdb1ea8ff7e1045be7f53a0646f4f7e7d34b92e1d4bbe7662e6be`.

- Seed: 20261003. The harness builds one deterministic token pool of 69,773 tokens and
  takes every prompt from it. Each prompt starts with a tag that holds the seed, the
  target, and the repeat.
- Targets and repeats: 2,048, 8,192, and 32,768 tokens, two repeats each. That is 6
  requests per arm.
- Output: up to 128 generated tokens per request, greedy.
- Order: the baseline arm ran first (2026-10-04 12:49 UTC), then the HTTP baseline
  (12:57 UTC), then the initial candidate arm (14:02 UTC), then the helper arm (14:05
  UTC), then the intermediate candidate arm on the `5e42229c…` binary (14:36 UTC), then
  the release arm on the `9a82265a…` binary (15:49 UTC), then the final arm on the
  `e9ad337a…` binary (16:25 UTC). The engine restarted before each arm. The harness
  verifies every runtime setting before it starts and aborts a row on any prompt reuse.
- Throughput: the engine's reported prompt time from its `DONE` record. Speed = fresh
  prompt tokens x 1000 / prompt time. Client wall time is not used.
- Thermal gate: before every request, both cards must stay at or below 55 °C for 10
  seconds. Every request met the gate; the wait was 10.0 seconds. Telemetry ran at 1 Hz.

All arms used byte-identical prompts. The prompt SHA-256 values follow.

## HTTP and API serving

HTTP requests go through the full service path, and the engine counts template tokens in
the prompt. HTTP numbers are therefore not comparable with the geni-protocol prefill arms
in this report.

### Matched serving pair on the final binary (32,768 context)

The final binary (`e9ad337a…`, 0.1.39) was served twice at a 32,768-token context: once
with one serving slot (`serving 1`) and once with two (`serving 2`), same model
configuration on the same cards. Both servers ran the identical client sweep: 128
generated tokens per request (all rounds finished with `length`), concurrency 1 / 2 / 4,
three repeats each. Raw results:
[`strata-v0139-http-solo32-completion.json`](../bench/results/2026-10-04-v100-upstream-v0139/strata-v0139-http-solo32-completion.json)
and
[`strata-v0139-http-parallel32-completion.json`](../bench/results/2026-10-04-v100-upstream-v0139/strata-v0139-http-parallel32-completion.json).

Concurrency criterion (explicit). A round counts as *concurrently served* only when all
three conditions hold together: (1) the streamed response intervals of the requests
overlap in wall time (stream-interval overlap), (2) the requests are marker-independent —
each request carries its own marker token, so an observed overlap cannot be an artifact of
the measurement script — and (3) the service monitor's queue telemetry shows a request
waiting while a slot is decoding (queue telemetry). The published proof records four
marker-independent requests (each output begins with its own marker token — CEDAR, MAPLE,
BIRCH, WILLOW — 256 tokens each, all outputs correct) on the two-slot server
(`e9ad337a…`, 0.1.39, `serving 2`). The token-emission intervals overlap by 6.1078 s
(requests 0-1) and 6.1937 s (requests 2-3), chained by a 0.208 s overlap (requests 1-3).
The retained monitor `live` snapshots record `.live.running == 2` in 261 of 263 samples
and `.live.waiting > 0` (a third request queued while both slots decode) in 138 of them.
[`strata-v0139-concurrency-proof.json`](../bench/results/2026-10-04-v100-upstream-v0139/strata-v0139-concurrency-proof.json)
is in the result directory; it is slimmed for publication — the per-snapshot request
arrays were omitted and the file describes what was removed.

| Server | Concurrency | Wall time (median) | TTFT (median) | Decode tok/s (median) |
| --- | ---: | ---: | ---: | ---: |
| One slot | 1 | 1.510 s | 87.3 ms | 90.0 |
| One slot | 2 | 3.256 s | 1,008.2 ms | 92.0 |
| One slot | 4 | 6.961 s | 2,666.4 ms | 89.8 |
| Two slots | 1 | 1.502 s | 84.3 ms | 90.3 |
| Two slots | 2 | 4.019 s | 353.3 ms | 34.8 |
| Two slots | 4 | 8.609 s | 2,446.0 ms | 32.8 |

The two servers used the same context and matched prompts; the two-slot server also ran
the API warm-up checks (chat, `/v1/responses`, Anthropic-style text, invalid-tool
rejection) before its benchmark rounds. Both sweeps are three repeats and warm after the
first request of each level. Values below are medians of the three repeats; the TTFT
medians include the level's slower first request (392 ms on the one-slot server, 293 ms on
the two-slot server).

No throughput speedup is claimed: at concurrency 2 and 4 the two-slot server's wall time
is 23.4% and 23.7% *longer* than the one-slot server (the slots share decode), while the
two servers match at concurrency 1 (1.510 s vs 1.502 s, ~90 tok/s decode). The measured
benefit is the second request's TTFT at concurrency 2: ~0.55-0.60 s with two slots versus
~1.74-1.99 s queued behind a full decode on one slot. At concurrency 4 both servers queue
the excess beyond their slots (TTFT ~2.5-2.7 s). These are serving observations of the
final binary, not a decode or quality comparison. A short API round against the two-slot
server also passed: chat smoke ("cobalt"), `/v1/responses`, and an Anthropic-style text
endpoint returned correct outputs, and a request with an invalid tool was rejected with
400.

## L3 conversation-cache verification (candidate `5e42229c…`)

The candidate binary (SHA-256 `5e42229c…`) was exercised with the disk conversation cache
in three scenarios: reuse (one engine: A, then an unrelated B, then the continuation A+),
restart (a second engine instance restores the stored A record and continues with A+), and
corrupt (one byte of the stored record is flipped before the restart). The configuration
matches the primary benchmark: 524,288-token context, INT8 KV, layer split 20, one serving
slot, host-RAM conversation cache disabled, 25 GiB disk store. The harness is
[`tools/conversation_cache_disk.py`](../../tools/conversation_cache_disk.py). The run used
16 paragraphs, and `--spec 1`, which the engine records as `spec=2` windows with
`mtp_max=1` and `spec_min_p 0.00`.

Prompts: A = 249 tokens, B = 61 tokens, A+ = 271 tokens (249 from A plus 22 new). Every
request generated greedy output. The recorded main-model state (the `L`, `gdn`, `ple`,
`tail`, `dead`, `pooled`, `pooled_full`, and `kv` hashes) was compared with the in-memory
baseline for every matching request.

| Scenario | Request | Read | Reused | Prompt ms | Output ids | vs baseline |
| --- | --- | ---: | ---: | ---: | --- | --- |

- Reuse and restart: the complete recorded state and the output ids are byte-identical to
  the in-memory baseline for A and A+. The A+ prompt phase read 22 new tokens and restored
  the stored A record; it took 1,307.9 ms (reuse) and 999.3 ms (restart) versus
  387.7-396.0 ms for the in-memory baseline. The engine logged one record read and one
  restore in these arms.
- Record: one parked conversation writes a single record of 240,715,914 bytes (5,706
  metadata bytes plus 240,710,112 payload bytes at payload offset 5,802, format version
  1). The restart instance reported one stored record, one recovery, and `reads 1`,
  `restored 1`.
- Corrupt: one byte (value 9) was flipped at record offset 120,360,858. The payload
  checksum (13814576321090674350) no longer matched; the engine logged `corrupt 1`,
  removed the record (`removed` true), and re-read the full 271-token prompt (reused 0,
  2,034.2 ms). The regenerated output ids are identical to the baseline. The regenerated
  state hashes differ from the baseline, because the state was rebuilt from a fresh read
  after the record was discarded. That is the verifier's contract: the corrupt scenario
  checks output parity only, while the reuse and restart scenarios require byte-exact
  recorded states. A summary print that labels the corrupt run "byte-exact" is
  misleading; the per-record checks above are the authoritative result.
- No arm logged a read failure, a shape discard, a write failure, or a cannot-open. The
  corruption counter rose exactly once in the corrupt arm and stayed 0 in the other arms.

This is a functional verification of the `5e42229c…` candidate, not a speed measurement.
The output is identical in every comparable request, and the reused-state arms are
byte-exact.

## Fallback serving smoke (candidate `5e42229c…`)

The `5e42229c…` candidate binary was started with two serving slots requested at 524,288
context and layer split 20. The startup log reports that the engine runs one slot in this
configuration, and the service status mirrors the effective count (`serving 1`, `requested
1`). The running engine reports 0.1.39 with 11,893 total expert slots (6,570 primary), 496
MiB of VRAM free, and the vision encoder launched and available. A solo launch of the same
binary and configuration reports identical resource counts (compare
`fallback-final/strata-v0139-fallback-final-status.json` with
`fallback-final/strata-v0139-solo512-final-status.json`): the one-slot fallback and the
solo launch use the same 11,893-slot / 6,570-primary / 496-MiB envelope. This is a smoke
observation: with the two-slot carve unavailable, the engine runs the one-slot
configuration instead of failing to start. No throughput comparison is made from it. (The
same fallback on the `9a82265a…` release binary at split 24 is verified under "512K batch
fallback".)

A short HTTP smoke against this server (128 generated tokens per request, one repeat each
at client concurrency 1 / 2 / 4, queued on the single slot) measured decode at 74.3 /
68.1 / 66.0 tok/s with draft acceptance 77 of 100, 99 of 128, and 76 of 122. The
Responses API, tool loop (`add_integers(17, 25)` -> "17 + 25 = **42**"), JSON schema, and
vision checks also pass on this server (`fallback-final/strata-v0139-api-extra-fallback-final.json`),
and a fresh browser chat rendered a 3-token "cobalt" reply with no errors. These values
are smoke observations of the fallback path, not a performance result.

## Conversation-disk restore precedence (regression; final `e9ad337a…`)

During the merge finalization a disk-restore defect was found in the conversation-cache
restorer. In an A/B/A+ batched sequence at 32,768 context (layer split 20, three slots,
1 GiB disk store; driver config in `cache-precedence/parity.json`), the `9a82265a…`
release binary restored the **stale** 25-token record for conversation A even though the
active slot had just handed back the valid 152 tokens of that conversation. The engine
logged a disk read hit of the 25-token record (`read …19 2 stages; hit 25 tokens`), and
the request resumed from the stale record: `prompt 172 tokens = 25 reused + 147 read` — 25
reused against the valid 152 tokens the slot had just handed back. The suite stopped with
exit 2. Raw evidence:
[`cache-precedence/before.log`](../bench/results/2026-10-04-v100-upstream-v0139/cache-precedence/before.log).

The final binary (`e9ad337a…`) fixes the restore precedence, verified on the same suite
(`cache-precedence/completion.log`, one engine session, 126.10 s wall):

- A2 (A+) restored the live conversation: `prompt 172 tokens = 152 reused + 20 read` —
  reused 152 of 152, the full bound.
- The next solo continuation reused 299 of 299 (`prompt 316 tokens = 299 reused + 17
  read`).
- All nine parity cases in the suite passed with byte-identical main-model state and
  output; the 18-token `itsTurn` checkpoint handed back its held tokens before the next
  turn resumed (the batched decode path offers no drafts, 0 of 0).
- The 4,021-token cold D request was pre-empted by B: it yielded after the 512-token `PP`,
  returned 1,024 tokens (`CANCEL 0`), and the replayed request recorded `prompt 4021
  tokens = 1024 reused + 2997 read`.
- Disk-store counters stayed consistent across the session (`records 4`, `evictions 11`,
  `corruptions 0`, no read/write failures).

The failing capture is the exact before/after pair for the fix; the release-binary capture
uses the same prompts, slots, store budget, and model configuration. The fix is on the
conversation-disk restore path only, which the prefill arms never touch (caches disabled),
so the prefill measurements of both binaries stand as recorded.

## 512K batch fallback (release `9a82265a…`)

At 524,288 context with layer split 24 and two serving slots requested, an earlier build
carved two slot sessions (3.66 GiB each on CUDA0, leaving 1.06 GiB free) and then failed
on the first request with `verify: instantiate: out of memory`
([`balanced512/before.log`](../bench/results/2026-10-04-v100-upstream-v0139/balanced512/before.log),
also the first session of `balanced512/engine.log`). The release binary (`9a82265a…`)
instead evaluates the second slot before starting: with two slots the CUDA0 expert cache
would drop to 293 slots, below the 414-slot floor the prompt path needs to lend its
buffers, so the engine warns and runs **one slot** (`serving 1`, `requested 1`). The full
safe session is the second session of
[`balanced512/engine.log`](../bench/results/2026-10-04-v100-upstream-v0139/balanced512/engine.log),
and the service status snapshot is
[`balanced512/safe-status.json`](../bench/results/2026-10-04-v100-upstream-v0139/balanced512/safe-status.json)
(engine SHA-256 `9a82265a…`, 0.1.39): 11,894 resident expert slots including 5,933
primary on CUDA0, 496 MiB of VRAM free, and the smoke reply `cobalt` with no errors. The
prompt path runs at an 8,192-token chunk with a 192-slot ring. This is a safety/startup
verification: the engine serves the one-slot configuration it can actually run instead of
starting a second slot that would OOM; no throughput comparison is made.

## Scope and limits

- Two repeats per size. These are small paired samples, not a statistical guarantee.
- One machine, one model, one quantization (native Q2_0), and INT8 KV, all at 524,288
  context with a single serving slot.
- The decode outputs are not bit-identical (see "Output parity"). The decode times and
  draft rates in the row table are measured telemetry, not a decode-quality or
  decode-speed comparison.
- The primary numbers in this report were measured with the final binary (SHA-256
  `e9ad337a…`), which includes the post-merge fixes to startup allocation and memory
  ownership: the MTP buffers are allocated before the batch slots (the earlier order
  raised an out-of-memory at a 524,288-token context with a batch of two slots at layer
  split 20); failed or excess CUDA carves and the pinned QSA metadata are freed through
  RAII ownership (a failed carve made the expert cache fall back to 3,956 slots instead of
  the full ~13,355, which slowed decoding); the global QSA ordinal is fixed on session
  release; and the last GPU's expert cache reserves the draft head's `mtp.bind_bytes`
  (178 MiB). The intermediate candidate (SHA-256 `5e42229c…`) carried these fixes; the
  release binary (SHA-256 `9a82265a…`) added the batch-slot fallback; the final binary
  (`e9ad337a…`) added the conversation-disk restore-precedence fix. The initial candidate
  binary (SHA-256 `2bffacd15…`) predates these fixes and is kept in the results only as
  the helper arm's comparison basis.
- The release-binary (`9a82265a…`) prefill numbers in this report are a real measurement
  of the build that preceded the final fix; they are not the final measurement and are
  superseded by the final-binary arm in the result table (see "Release measurement").
- The temperature and power values apply to this passively cooled machine only.
- Maintainer-run verification on the final merge tree: CTest registered 84 cases; 81 were
  selected for this host (3 excluded) and every executed case passed — 79 passed and 2
  skipped (both SM80-only prefill-fused kernels), a 100% pass rate among executed cases,
  in 77.70 s, with the same core libraries as the measured binary and with `PYTHONPATH`
  pointing at the external `gguf-py` package. The core test executables were unchanged
  before and after the final main cache fix; an earlier run of the same selection
  (76.81 s) is superseded. The three excluded cases are the AVX-512-only
  `expert_multi_test` and `expert_parity` (this CPU has no AVX-512) and the legacy PLE
  capture test that is not present in this tree. The Python serve suite (275
  cases) and tools suite (396 cases) pass unchanged; both were green before the harness
  revisions made for this report. These runs are separate from the benchmark evidence in
  this report.

## Reproduction

Build the candidate from the merge branch with CUDA 12.8:

```sh
cmake -S "$SOURCE" -B "$BUILD" -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_CUDA_COMPILER=/usr/local/cuda-12.8/bin/nvcc \
  -DCMAKE_CUDA_ARCHITECTURES=70 -DSTRATA_ENABLE_CUDA=ON \
  -DSTRATA_BUILD_TESTS=ON
cmake --build "$BUILD" --target strata -j 8
```

Run the prefill arms with the public harness. Keep the model configuration identical and
change only the engine executable and the arm label:

```sh
.venv/bin/python bench/run_v100_prefill.py --arm-label fork-main \
  --exe "$BASELINE_ENGINE" --targets 2048,8192,32768 \
  --repeats 2 --seed 20261003 --max-new 128 --out "$OUT"
.venv/bin/python bench/run_v100_prefill.py --arm-label upstream-v0139-completion \
  --exe "$FINAL_ENGINE" --targets 2048,8192,32768 \
  --repeats 2 --seed 20261003 --max-new 128 --out "$OUT"
.venv/bin/python bench/run_v100_prefill.py --arm-label upstream-v0139-release \
  --exe "$RELEASE_ENGINE" --targets 2048,8192,32768 \
  --repeats 2 --seed 20261003 --max-new 128 --out "$OUT"
.venv/bin/python bench/run_v100_prefill.py --compare \
  "$OUT/result-fork-main.json" "$OUT/result-upstream-v0139-completion.json"
```

Use the same `--targets` and `--repeats` values as the measured run, because the token
pool length follows the seed and the largest target. Store private model paths and
authentication in the local configuration only. The original service binary is restored
after the test; no candidate binary replaces the installed engine.
