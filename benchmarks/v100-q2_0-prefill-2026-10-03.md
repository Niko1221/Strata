# V100: INT8-KV prefill with FP16 tensor-core experts

## Result

The change raises prompt (prefill) throughput on two Tesla V100 cards. All five prompt sizes gain at
least 20% more tokens per second (24.63% to 35.43%). Each request generated one token, so decode is not
measured. The change is **not bit-exact**: the first generated token is identical in 14 of the 15 paired
requests.

| Prompt tokens | Baseline prefill (median) | Candidate prefill (median) | Less time | Baseline speed | Candidate speed | Change |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 2,048 | 3,663.4 ms | 2,910.7 ms | 20.55% | 559.04 tok/s | 703.61 tok/s | +25.86% |
| 4,096 | 5,039.0 ms | 3,794.8 ms | 24.69% | 812.86 tok/s | 1,079.37 tok/s | +32.79% |
| 8,192 | 7,810.4 ms | 5,767.0 ms | 26.16% | 1,048.86 tok/s | 1,420.50 tok/s | +35.43% |
| 16,384 | 11,052.3 ms | 8,517.8 ms | 22.93% | 1,482.41 tok/s | 1,923.50 tok/s | +29.75% |
| 32,768 | 18,078.8 ms | 14,506.0 ms | 19.76% | 1,812.51 tok/s | 2,258.93 tok/s | +24.63% |

Each value is the median of three fresh requests. The candidate column is the arm with no override
(`candidate-default192-r3`), which uses the compact walk's 192-slot ring default. A repeat of the
baseline arm on the same build moved the median speed by at most 0.172%. The control drift is therefore
smaller than the measured change.

At 2,048 tokens the engine batches 2,047 prompt tokens (its `PP` record shows 2,047 of 2,048; the last
token is processed separately). That is below the compact walk's 2,048-token stream floor, so the
2,048-token row runs the int8 MMQ small-chunk path, not the FP16 tensor-core products. Its gain comes
from the new staging, buffer-sizing, and refill policies. Every larger size uses the compact walk.

## Method

The harness [`bench/run_v100_prefill.py`](../bench/run_v100_prefill.py) speaks the engine's own
stdin/stdout serve protocol. It sends the token ids directly, so the engine's prompt length equals the
requested length: there is no template and no probe request. The HTTP harness
[`bench/run_v100_bench.py`](../bench/run_v100_bench.py) is not used here.

The baseline arm recorded harness revision
`9cf7e089a1b146b5f13e159c6dd0961668ec4a23b29f77de3fb8df3f69ef10f2`; the final candidate arm recorded
revision `ae03df48882fdb1ea8ff7e1045be7f53a0646f4f7e7d34b92e1d4bbe7662e6be`. Both revisions produced
the same prompt plan (the same SHA-256 for all 15 prompts) and the same settings check. The recorded
result schema of the two revisions differs only in one summary field: an unused within-arm output-parity
flag, which the final revision removed.

- Seed: 20261003. The harness builds one deterministic token pool of 106,800 tokens and takes every
  prompt from it. Each prompt starts with a tag that holds the seed, the target, and the repeat.
- Targets and repeats: 2,048, 4,096, 8,192, 16,384, and 32,768 tokens, three repeats each. That is 15
  requests per arm.
- Output: one generated token per request, greedy.
- Order: the baseline arm ran first, then the candidate arm. The engine restarted before each arm. The
  harness verifies every runtime setting before it starts and aborts a row on any prompt reuse.
- Throughput: the engine's reported prompt time from its `DONE` record. Speed = fresh prompt tokens
  x 1000 / prompt time. Client wall time is not used.
- Thermal gate: before every request, both cards must stay at or below 55 °C for 10 seconds. Every
  request met the gate; the wait was 10.0 seconds. Telemetry ran at 1 Hz.

Both arms used byte-identical prompts. The prompt SHA-256 values follow.

## What changed

The candidate moves the routed prompt experts of a native Q2_0 pack to FP16 tensor-core products
(`mma.m8n8k4`) with FP32 accumulation on Volta (`src/prefill/moe_fp16tc.cu`,
`include/strata/prefill/moe_fp16tc.hpp`).

- The activations are the same q8_1 codes and float scales that the int8 MMQ path uses. The kernel
  rounds each activation scale to FP16, then multiplies it by the signed code in FP16. The weight
  scales are already FP16. The operand rounding and the FP32 accumulation differ from MMQ, so the
  outputs are not bit-identical.
- The gate/up and hidden buffers hold a compact row capacity instead of one row per routed token. The
  walk splits a 16-expert group into sub-batches that share one compact scratch subgroup.
- The sorted activation array is retained. The last small chunk keeps the int8 MMQ path with a safe
  size.
- On this path the compact walk selects a 192-slot streamed ring and lowers the chunk size from which
  every expert streams (2,048 tokens). The other layouts keep the pinned-share rule.
  `STRATA_PREFILL_RING` and `STRATA_PREFILL_STREAM_MIN` override both values.
- A layer split's non-last stage now queues the refill of the expert-cache slots that it lent the prompt
  path before it waits for the last stage. The stage synchronizes both of its streams first, and only
  the final batched segment may act. The default applies to a native Q2_0 pack on a Volta-only split.
  `STRATA_PREFILL_REFILL_OVERLAP=0` disables the overlap; the serial and blocking refill modes bypass
  it.
- `STRATA_PREFILL_FP16TC=0` keeps the int8 MMQ reference on every device. The change applies to compute
  capability 7.0 only; other architectures and packs keep their existing paths.

The Volta tensor-core avenue follows research on SM70 tensor cores in
[rog77/ninfer-v100](https://github.com/rog77/ninfer-v100). The kernels described here are a Strata
implementation.

### Streamed-ring tuning

The compact walk splits a 16-expert group across a ring of at least 48 slots. A small sweep set the ring
default on the eligible path. At 32,768 tokens, with three repeats each and an explicit
`STRATA_PREFILL_RING` override, the ring measured:

| Ring slots | 32K prefill (median) |
| ---: | ---: |
| 48 | 1,970.88 tok/s |
| 96 | 2,173.10 tok/s |
| 192 | 2,259.32 tok/s |

The 48-slot ring loses at the large sizes, so the source default on this path is 192 slots, with a
2,048-token stream floor. The other layouts keep the pinned-share rule.

## Correctness

`prefill_fp16tc_test` passed on both V100 cards. It compares the new path and the int8 MMQ path with a
double-precision reference on random native Q2_0 expert blobs and random routing.

| Comparison | Relative RMS | Worst row |
| --- | ---: | ---: |
| Int8 MMQ against the FP32 reference | 1.074e-02 | 3.881e-02 |
| FP16 tensor core against the FP32 reference | 1.073e-02 | 3.798e-02 |
| FP16 tensor core against int8 MMQ | 9.674e-04 | 6.332e-03 |

The gate of the test is that the new path's error stays within 1.5 times the MMQ RMS and 2 times its
worst row. The intermediate gate/up and hidden values differ by 2.932e-04 and 4.271e-04 relative RMS.
Every compact sub-group reproduced the full-group rows exactly. A compute-sanitizer memcheck run of the
same test ran on both cards and reported `ERROR SUMMARY: 0 errors`:

```sh
/usr/local/cuda-12.8/bin/compute-sanitizer --tool memcheck --error-exitcode 99 \
  "$BUILD/prefill_fp16tc_test"
```

A one-time semantic smoke ran 8 checks per arm: retrieval at 10%, 50%, and 90% depth at 2,048 and
32,768 tokens, plus one arithmetic question at each length, with up to 128 generated tokens. Both arms
passed all 8 checks. The two arms produced the same output token ids for all 8 requests, and both used
the same plan (SHA-256 `e2786b863ea184e1277c60ea68dcccf71929d041648933ebfd2d02c04d1c851b`). This is a
smoke check, not a quality measurement.

The first generated token is identical in 14 of the 15 paired requests. At 16,384 tokens, repeat 2
produced token 19 in the baseline and token 16 in the candidate. The new path is not bit-exact. Small
numerical changes can change generated text. This report does not claim unchanged perplexity or
long-generation quality.

## Scope and limits

- The kernels select on compute capability 7.0 (Volta), not on a product name. Only two Tesla
  V100-PCIE-16GB cards were tested. Other compute capability 7.0 parts (for example, Titan V) are
  eligible but were not tested.
- One machine, one model, one quantization (native Q2_0), and INT8 KV.
- Three repeats per size. These are small paired samples, not a statistical guarantee.
- Decode was not measured, because each request generated one token.
- The temperature and power values apply to this passively cooled machine only.

## Reproduction

Build the candidate with CUDA 12.8:

```sh
cmake -S "$SOURCE" -B "$BUILD" -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_CUDA_COMPILER=/usr/local/cuda-12.8/bin/nvcc \
  -DCMAKE_CUDA_ARCHITECTURES=70 -DSTRATA_ENABLE_CUDA=ON \
  -DSTRATA_BUILD_TESTS=ON
cmake --build "$BUILD" --target strata prefill_fp16tc_test -j 8
ctest --test-dir "$BUILD" -R '^prefill_fp16tc_test$' --output-on-failure
```

Add `-DSTRATA_GGML_DIR="$GGML_SOURCE"` to build against a supplied ggml source tree. Without that
option, CMake fetches the revision recorded in `third_party/ggml/VERSION.txt`
(`3cf03257f219afbe7334045ff7c6a06ac68c627d`). The measured build used the in-tree
`third_party/llama.cpp` copy; that copy is not a separate Git checkout, so no local revision is recorded
for it.

Run both arms with the public harness. Keep the model configuration identical and change only the
engine executable:

```sh
.venv/bin/python bench/run_v100_prefill.py --arm-label baseline-final-r3 \
  --exe "$BASELINE_ENGINE" --targets 2048,4096,8192,16384,32768 \
  --repeats 3 --seed 20261003 --max-new 1 --out "$OUT"
.venv/bin/python bench/run_v100_prefill.py --arm-label candidate-default192-r3 \
  --exe "$CANDIDATE_ENGINE" --targets 2048,4096,8192,16384,32768 \
  --repeats 3 --seed 20261003 --max-new 1 --out "$OUT"
.venv/bin/python bench/run_v100_prefill.py --compare \
  "$OUT/result-baseline-final-r3.json" "$OUT/result-candidate-default192-r3.json"
```

Use the same `--targets` and `--repeats` values as the measured run, because the token pool length
follows the seed and the largest target. Add `--env STRATA_PREFILL_FP16TC=0` to the candidate arm to
reproduce the int8 reference path in the candidate build. Store private model paths and authentication
in the local configuration only. The original service binary is restored after the test; no candidate
binary replaces the installed engine. The restored service reported `status ok` with
`max_context 524288`, and the installed engine kept its original SHA-256
(`b13c79f18336ac7f6a947739d2554b6c2f1c5a82b15f326403abc32446dcc6ef`).
