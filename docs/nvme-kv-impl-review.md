# NVMe KV cold tier — implementation review (read-only)

Scope reviewed: `include/strata/platform/kv_nvme.hpp`, `src/platform/kv_nvme.cpp` (new, untracked), the `generate.cpp` integration (working-tree diff vs HEAD, +266 lines), `include/strata/core/mtp.hpp` (`kv_state_mut()`), `tools/nvme_p0_test.sh`, `tools/nvme_steps123_test.sh`, cross-checked against `core/session.cpp`, `core/layer.cpp` (`qsa_state_init`/`qsa_state_zero`), `kernels/cuda/kv_stream.cu`, `core/mtp.cpp` (`kv_restore`), `core/verify.cpp`, and the design doc §0–§11.

`sizeof(NvmeHeader)` = 104 bytes (kv_nvme.hpp:20-33: 4+4+8+8+4+4 + 8×8 + 8, all naturally aligned). This number matters below.

## Correct (verified, with evidence)

- **Segment order dump vs restore is identical.** Dump order (kv_nvme.cpp:126-156): header, ids, imgs, gdn, ple, then per QSA layer {kv arrays (2 for f16/q4, 4 for int8 incl. both scale arrays, same order as `state_hash_line`'s `kv_arrays`), idx_pooled, idx_tail, idx_dead, idx_block_pos}, then MTP host-KV arrays. Restore walks the exact same sequence (kv_nvme.cpp:233-258). Sizes are computed by the same formulas in both directions.
- **The size walk is self-checking.** Any geometry/config drift that changes any segment size (idx_pooled_rows, PLE presence, drafter ring size, kv format, head counts) ends with `at != buf.size()` → refusal (kv_nvme.cpp:260-262). There is no plausible silent-misalignment accept path; the header check (kv_nvme.cpp:213-218) is belt, the walk is suspenders. Byte math casts to `size_t` before every multiplication — no overflow at these magnitudes.
- **The persisted set matches design §0.** All of: host KV in every format (f16 / int8 codes+both scales / q4), `idx_pooled`, `idx_tail`, `idx_dead`, `idx_block_pos`, `gdn_state`, `ple_hist`, `ple_prev` (restored with checkpoint_restore's exact semantics: oldest-first, -1 padding — kv_nvme.cpp:280-281 vs generate.cpp:680-682), and the MTP drafter host-KV copy with `mtp.kv_restore(resume)` ring refill on both the startup path (generate.cpp:2658) and the promote path (generate.cpp:2936). Correctly *not* persisted: `step`/`pos_dev`/`host_step`/`host_pos`/`attention_status` (per-token scratch refilled by `stage_token`/`qsa_step_fill`), rope tables (geometry-only), `ple_token` (per-token in the serve path, managed by `verify.cpp:948-949`).
- **`kv_stream_reset` per layer after restore** (kv_nvme.cpp:285-286) reproduces `qsa_state_zero`'s "nothing resident" contract (layer.cpp:676); stale VRAM slot contents are never read before a refill (documented invariant, layer.cpp:673-675), and the final `cudaDeviceSynchronize` (kv_nvme.cpp:283) orders the reset kernel before the next request's work.
- **The walk-then-apply design does give atomicity for the realistic corruption case** (truncated/torn file): `take()` (kv_nvme.cpp:202-208) never reads past `buf.size()`, `bad` latches, and nothing is applied until the whole walk succeeded.
- **The `mtp_host` fseek patch-up is correct** (kv_nvme.cpp:170-174): `fseek`/`fwrite` interleave legally on one `FILE*`, the offset is computed from the struct itself, and `SEEK_END` restores the append position before `fflush`/`fsync`. The dump/restore array-count symmetry (`mtp_arrays == h.mtp_host`, kv_nvme.cpp:260) also catches a drafter that fell back to fully-resident between dump and restore.
- **`state_hash_line` refactor is a byte-for-byte extraction** of the old inline STRATA_STATE_HASH block (verified line-by-line in the working-tree diff); behavior preserved.
- **Supersede semantics are correct for the branch scenario.** Supersede only fires when `last_ids_` is a *strict prefix* of the new ids (kv_nvme.cpp:335-336). A 3902-checkpoint-restore + divergence produces a non-prefix sibling: the 4235 entry is neither wrongly superseded nor wrongly dropped, and both entries remain independently matchable (each requires *full* prefix match, so a prompt can match at most one branch). `enforce_cap`/`drop` correctly maintain `total_` and clear the `last_path_` bookkeeping (kv_nvme.cpp:385, 400).
- **`KvNvmeStore::dump`'s caller synchronizes** (`cudaDeviceSynchronize()` at generate.cpp:3240) before the D2H reads — the checkpoint_save contract stated in kv_nvme.hpp is honored on this path.
- One-session-at-a-time serve means no concurrency hazards: promote runs between requests with the device idle, and the restore's device-wide sync precedes the request's first kernels.

## Findings

### P1 — must fix before this touches the live server

**P1-1. The P0 oracle script is stale against the v2 header — the Step-0 evidence does not match the checked-in code.**
`tools/nvme_p0_test.sh:67` extracts ids with `f.seek(96)` (and line 84's corruption offset comment says "header(96)"), but the v2 header with `mtp_host` is 104 bytes — which `tools/nvme_steps123_test.sh:60` correctly uses (`f.seek(104)`). With the current code, p0's extracted `full_ids.txt` = [lo32(mtp_host), hi32(mtp_host), ids[0..L-3]] — shifted by 8 bytes. B's prompt then does *not* prefix-match the restored session: `starts_with` fails at token 0 (prompt[0] = the mtp array count, e.g. 4), so B resumes 0, and the "same-process live continuation" token gate compares two *full re-prefills* (vacuously equal), not a live continuation. Either the recorded passing run predates the `mtp_host`/v2 header (in which case **the current code has never passed the Step-0 gate "bit-exact or stop"**), or it ran with these gates failing. Only the prompt-independent `H_Bpost == H_A` restore-exactness gate is unaffected by the offset. Fix: 96→104 at p0:67 and p0:84 (comment), then re-run the oracle against the current binary. Until then, treat the P0 evidence as unconfirmed for v2.

**P1-2. A failed promote can leave the session half-written and the request proceeds anyway.**
`nvme_restore`'s atomicity claim covers only the *walk*. The *apply* loop (kv_nvme.cpp:267-277) can fail mid-way: a `cudaMemcpy` H2D failure between device segments, or the final `cudaDeviceSynchronize` at kv_nvme.cpp:283 returning failure *after everything was applied*. The caller (generate.cpp:2887-2891) logs, drops the entry, and falls through with the *pre-promote* `resume`/`from_live`: if a checkpoint had matched (`resume > 0`, `from_live == false`), `checkpoint_restore` re-fixes gdn/ple/idx_tail but **not** idx_pooled/idx_dead/idx_block_pos/host KV — a mix of two states at two lengths; if `from_live` was true, gdn/ple/idx_* are a half-mix of the snapshot (state at EL) and the live session (state at `resume`). Both are exactly the "fluent-but-wrong tokens, not a crash" class the design §0 warns about. Low probability (memcpy failure), silent-wrong severity. Smallest fix: in the failure branch at generate.cpp:2888-2891, force the clean path — `resume = 0; from_live = false;` and let the existing `resume == 0` branch `session_zero` the session (checks pruning already handles the rest). Alternative: stage the device applies into host temp buffers and commit only on full success.

**P1-3. `--kv-nvme` with the default (non-streamed) KV is a no-op tier — agreed v1 §0.3 not implemented.**
The agreed design says "Force streamed mode under `--kv-nvme` (a `qsa_set_kv_resident` floor) so the host copy always exists; closes the kv_mode 0 gap." There is no floor anywhere (no `qsa_set_kv_resident` call tied to `o.kv_nvme`). Instead, `nvme_dump` refuses kv_mode 0 (kv_nvme.cpp:112-114) and every DONE logs "kv-nvme dump failed: KV is fully resident…" (generate.cpp:3243-3245) while the store banner printed at startup (generate.cpp:2643) says everything is fine. Since `--kv-resident` defaults to 0, the most natural invocation (`--kv-nvme DIR` alone) stores nothing and promotes nothing, loudly. Fix: when `o.kv_nvme` is set, raise `o.kv_resident` to a floor before `qsa_set_kv_resident(o.kv_resident)` (generate.cpp:1069), or refuse at startup with an actionable message.

**P1-4. Malformed store files can kill the serve process (uncaught exceptions) instead of being refused.**
- `KvNvmeStore::open` (kv_nvme.cpp:306): `ids.assign((size_t) h.L, 0)` runs after only magic/version/format/n_* checks; a file with corrupted `L` (negative or huge) throws `std::length_error`/`bad_alloc` out of `open()` → uncaught → `std::terminate` at startup. A single corrupt file bricks every restart until manual cleanup.
- `nvme_restore` (kv_nvme.cpp:221): `imgs.assign((size_t) h.n_imgs, {})` before any validation of `n_imgs` — same class; the promote path's graceful "reading the prompt instead" (generate.cpp:2889) never sees this because it's an exception, not a `false` return.
- `nvme_restore` (kv_nvme.cpp:192-196): `const long fsize = std::ftell(f);` then `std::vector<uint8_t> buf((size_t) fsize);` is constructed *before* the `fsize < sizeof(NvmeHeader)` check. On `ftell` failure (or `--nvme-restore <directory>`, which `fopen`s successfully on Linux) `fsize == -1` → `(size_t)-1` allocation → throw. Also `long` is 32-bit on Windows: an f16 128K-context snapshot (~3.3 GiB, doc §5.3) overflows `ftell` there.
Fix: validate/clamp `h.L`/`h.n_imgs` (and the ids read) before the big assigns; move the `buf` construction after the size check; use `ftello`/`_ftelli64`; optionally wrap the store's file handling in try/catch → `err`.

### P2 — fix before/around release, report-only if deferred

**P2-1. Promote picks the *last* matching entry in iteration order, not the longest.** generate.cpp:2873-2885: `best = &e;` is assigned on every match that merely exceeds `resume`; the comment "strictly longer than every match before it: the longest prefix wins" is not what the code does. Cross-restart prefix-siblings (see P2-2) *can* both match one prompt, and directory scan order is unspecified. Output stays correct (a shorter prefix is a valid resume), but TTFT silently degrades. One-line fix: `if (best == nullptr || EL > best->L) best = &e;`.

**P2-2. Cross-restart supersede gap → dominated snapshots accumulate.** `last_ids_`/`last_path_` are per-process (kv_nvme.cpp:335-348). After a restart, a promote→DONE writes a new file even when a stored entry's ids are a strict prefix of the new ids; nothing ever deletes the dominated entry. Growth is bounded only by the cap (default 100 GB ≈ 125 files/conversation); with `--kv-nvme-max 0` it is unbounded. Fix: in `dump()`, supersede (delete) any stored entry with `e.cvec == cvec` whose ids are a strict prefix of the new ids — any prompt matching the shorter also matches the longer, so it is strictly dominated and safe to drop; the 3902-divergence sibling is untouched by this rule (non-prefix).

**P2-3. Spike `--nvme-dump` path lacks the device sync.** generate.cpp:3226-3234 has no `cudaDeviceSynchronize()`, unlike the kvstore path at generate.cpp:3240. The host KV pools are UVA device-mapped pinned memory written by GPU kernels; `nvme_dump` reads them with plain CPU `fwrite` (kv_nvme.cpp:150-151), so without a sync the dump can capture stale cells. It passes today only because the P0 test always sets `STRATA_STATE_HASH=1`, whose `state_hash_line` syncs first (generate.cpp:695). Add the sync (or call it out in the flag's comment).

**P2-4. Misaligned/aliasing cast of the imgs segment.** kv_nvme.cpp:223-226 casts `buf.data() + at` (offset 104 + 4·L) to `const std::pair<int64_t,uint64_t>*` — 8-byte-aligned only when L is even; strictly-aliasing/misalignment UB (works on x86, can trap on ARM/MSVC debug). `memcpy` into a local vector like the ids are logically used (they already go through `assign(imgp, imgp + h.n_imgs)` — replace the pointer dereference range with a memcpy).

**P2-5. Failed dumps leave partial files that the next `open()` accepts as entries.** `nvme_dump` failures (disk full, mid-write crash, the failed `mtp_host` patch-up) leave a file with a valid header + ids; `open()` scans it in (kv_nvme.cpp:296-318) and counts its bytes toward `total_`/the cap — a junk multi-GB file can evict *good* entries before anyone notices. It is only cleaned when a promote tries it, fails, and drops it. Fix: `std::remove(path)` on any `nvme_dump` failure inside `KvNvmeStore::dump` (and have `open()` log skipped files).

**P2-6. Exact-match skip ignores `imgs`.** kv_nvme.cpp:330 skips the write when ids+cvec match; two sessions with identical pad-token ids but different images (same grid) keep the *old* entry with the old `imgs`/KV. Correctness is preserved by the promote guard (`imgs_below(req_imgs, EL) == eimgs`), so this is a missed promote plus a stale key, not wrongness. Compare `imgs` in the skip too.

**P2-7. mtime refresh and LRU edges.** The exact-match skip refreshes only the in-memory `e.mtime` (kv_nvme.cpp:331), not the file's — recency is lost across restarts, so LRU order degrades to file order. `enforce_cap` never evicts the last entry even if it alone exceeds the cap (kv_nvme.cpp:392, `entries_.size() > 1`) — the observed "0.83 GiB under a 1 GB cap" is this policy, not the cap; a single 44 GB snapshot under a 1 GB cap is kept. Deliberate? Document it.

**P2-8. Diagnostics: refusals masquerade as "truncated snapshot".** The header does not record idx_pooled_rows, PLE presence, or the drafter's ring size; all of those mismatches (correctly refused by the size walk) surface as `nvme_restore: truncated snapshot` (kv_nvme.cpp:260) rather than "geometry/format mismatch". Also `open()`'s tag check (kv_nvme.cpp:299-302) is a subset of restore's (no idx_dim/page_size/idx_block/max_cells), so entries are admitted that will always fail at restore. Cosmetic, but it will cost someone an afternoon.

**P2-9. Resource/platform edges.** Whole-file read into RAM is unbounded (no sanity cap on `fsize` before the ~1.7–3.3 GB allocation — fine on the 60 GB box, but a stray huge `kv-*` file OOMs); `fsync` is POSIX-only (kv_nvme.cpp:177-179, no `_commit`/`FlushFileBuffers` on the Windows build — the crash-consistency claim in the comment is not honored there); `getpid`/`_stat` fallbacks and `std::filesystem` are fine on both platforms.

**P2-10. Harness and flag nits.** Both scripts always exit 0: `nvme_p0_test.sh` has no FAIL aggregation at all, and `nvme_steps123_test.sh` ends with `[ … ] && echo "ALL PASS" || echo "SOME FAILURES"` — the final `echo` returns 0, so CI must parse stdout. `--kv-nvme-max` (generate.cpp:969) accepts `atoll` garbage, 0 and negatives, all silently meaning "unlimited"; no validation and no `--help` entry for any of the four flags (the auto-tier flags are documented only in the Options struct comment). The startup banner prints "cap 0 GB" for unlimited. Also minor: promote is not gated on `o.prompt_cache > 0` while dump is (`live_ok = o.prompt_cache > 0`) — promote-without-cache works, dump-without-cache doesn't; harmless but asymmetric.

## Verdict and ranked fixes

**Merge verdict: OK with notes** — the core dump/restore walk is sound, self-checking, and covers the complete agreed v1 persisted set; no happy-path correctness bug found. But do **not** enable `--kv-nvme` on the live server before the P1 list is closed, and the Step-0 "bit-exact or stop" gate must be re-established (P1-1) because the checked-in oracle cannot pass against the checked-in v2 header.

Ranked, must-fix first:
1. **P1-1** — fix `tools/nvme_p0_test.sh:67,84` (96→104) and re-run the oracle; the v2 code's bit-exactness evidence is currently untrustworthy.
2. **P1-2** — on promote failure, force `resume = 0; from_live = false;` (session_zero path) at generate.cpp:2888-2891; three lines, closes the silent-corruption path.
3. **P1-3** — implement the agreed `qsa_set_kv_resident` floor under `--kv-nvme` (generate.cpp:1065-1069) or refuse at startup; the default flag combination is currently a no-op tier.
4. **P1-4** — validate `h.L`/`h.n_imgs`/`fsize` before the big allocations in `open()`/`nvme_restore` (kv_nvme.cpp:306, 221, 192-196); a corrupt store file must not be able to crash-loop the server.

Nice-to-have (in order of value): P2-1 (longest-match, one line), P2-2 (prefix-supersede across restarts), P2-5 (unlink failed dumps), P2-3 (spike dump sync), P2-4 (imgs memcpy), P2-8 (better refusal diagnostics), P2-7, P2-6, P2-9, P2-10.
