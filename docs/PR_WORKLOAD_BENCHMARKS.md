# Essay and coding throughput on RTX 5090

Three paired runs per workload on an **undervolted RTX 5090, Ryzen 9 9950X3D,
48 GB DDR5-6000**, with four concurrent requests. Rates below are aggregate
emitted output tokens per second, not speculative rows or per-agent rates.

| Workload | Measurement | Baseline TPS | Candidate TPS | Gain |
| --- | --- | ---: | ---: | ---: |
| Essay writing | Four-stream decode | 146.2 | 200.1 | 1.37x |
| Essay writing | Whole bounded run | 141.1 | 189.2 | 1.34x |
| Tool-driven coding | Four-stream decode | 167.1 | 325.7 | 1.95x |
| Tool-driven coding | Whole bounded run | 137.3 | 221.5 | 1.61x |

The baseline is upstream v0.1.40.1 **plus a two-line shared-MTP-head metadata
fix** already present in this PR; unmodified upstream fails to admit these MTP
requests. Both arms keep concurrent MTP enabled. Thinking is disabled for this
bounded fixture; normal optimized CPU kernels and adaptation remain enabled.

The coding tool loop checks syntax and structure, not functional correctness.
Baseline modules passed 12/12 structure checks; candidate modules passed 11/12.
Ten baseline and nine candidate agents reached the six-turn cap; only two and
three, respectively, naturally ended with a passing checked module. Agents
often made more tool calls after checks passed. These are throughput results,
not proof of faster correct task completion or equal model quality. Different
essay lengths also preclude treating elapsed time alone as an equal-work gain.



## Setup

- Undervolted NVIDIA RTX 5090, Ryzen 9 9950X3D, 48 GB DDR5-6000.
  RAM speed was confirmed by the owner and Windows. The existing undervolt
  was retained; its voltage curve was not measured or changed.
- Windows, driver 610.88, CUDA 13, MSVC 14.32, Release, sm120-real.
- Swift 1.5 IQ2_XS, c=4, 98,304-token context per request, int8 KV,
  2,560 MiB VRAM reserve. Both arms requested 10,500 experts and loaded
  11,022 after allocation granularity. No cache-cut fallback was observed.
- Temperature .85, top-p .95, top-k 20; paired seeds 123, 456, 789.
  Thinking is disabled for these bounded generation workloads. Normal
  optimized CPU kernels and adaptive caching remain enabled.
- Each measured run starts a fresh engine, generates a 256-token warm-up,
  then runs four clients. Engine load and warm-up are excluded. Arm order
  alternates. No compiler or second inference engine runs during measurement.

## Reference

The unmodified upstream v0.1.40.1 engine (82f46a8) fails on this setup when
concurrent MTP first admits a request: `unsupported native MMVQ GGML type`.
The shared MTP drafter copied the head pointer without its quantization type.
That failed run is retained separately and contributes no throughput result.

The measured reference is **upstream v0.1.40.1 plus the two-line shared-head
metadata fix**, commit dce4b05. It copies `dhead_type_` and `dvocab_host_` from
the shared drafter. Those lines are already present in the performance PR.
Giving them to the reference keeps concurrent MTP enabled and avoids treating
a baseline failure as a performance advantage. This is explicitly not a claim
about an unmodified upstream binary.

Reference: `--batch 4 --batch-mtp`. Both use `--spec 4 --spec-min-p .5`;
upstream batching verifies one proposal per slot, while the candidate can
verify up to three proposals per slot within its sixteen-row budget.
Candidate adds `--batch-spec 4 --batch-rows 16 --batch-spec-fixed
--batch-draft-overlap --batch-suffix --batch-expert-merge --batch-adapt
--batch-pcie-frac 0`, with `STRATA_BATCH_DENSE_PARALLEL=1`.
Both use `STRATA_QFUSE=0` and default `STRATA_IQ_MT_MIN=2`.
The 96K context is configured capacity; these short prompts and tool histories
do not constitute a full-window or long-prefill stress benchmark.
The candidate's additional adaptation and PCIe choices are part of the
configuration being evaluated, not isolated single-kernel improvements.

## Workloads

**Essay writing:** four different topics: urban heat and inequality, astronomy,
public transport, and public libraries. Each asks for a developed essay, with
a 2,048-output-token cap. The model can stop earlier. This measures bounded
essay generation; it does not assert every essay reaches the requested length.

**Agentic coding fixture:** four independent agents read a task file, write a
Python module with two dataclasses, explicit validators/serializers and ten
unittest methods, and call a checking tool. Each agent has an isolated in-memory
workspace. Read/write/check calls are generated by the model and their real
results are fed into its next turn; subsequent requests interleave with other
agents' output. There is a six-turn limit and a 3,072-output-token limit per
turn. The checker compiles syntax and checks AST structure; it never executes
the generated Python or its tests. This is not a DSH session, SWE-bench result,
or functional code-quality benchmark.

The same native-protocol driver, tokenizer, chat template and tool parser are
used for both engine builds. Full token IDs, receipt timestamps, prompts,
outputs and tool results are retained. Initial prompts are identical within
each pair; subsequent tool histories and outputs can differ. Identical seeds
do not guarantee identical outputs under different batching/adaptation.

## Metrics

- **Four-stream decode TPS:** emitted tokens divided by time while all four
  slots are active and no request admission is in progress. This measures
  aggregate output, not per-stream rate or speculative verification rows.
- **Whole-run TPS:** emitted tokens divided by elapsed time from first request
  submission to the end of the bounded run, including prompt reads, tool
  handling and periods with fewer than four active slots.
- Each table reports medians of three paired runs. Individual values, token
  counts, TTFT and gap measurements are retained in the summary. Ratios are
  ratios of medians, not confidence intervals.

Different output lengths and tool behavior mean elapsed-time differences alone
are not equal-work task-completion speedups. Repeated calls, turn limits and
failed structure checks must be shown alongside throughput. These measurements
do not establish numerical parity or quality equivalence; those are separate
qualifications.

## Harness correction and exclusions

The first coding pair used a harness that retained the native `<|im_end|>` token
in tool conversation history. Both affected runs are archived under
`invalid-harness-v1` and excluded, regardless of their rates. The driver now
strips terminal markers, as the server's detokenizer does. Only that coding
pair was repeated. Single-turn essay prompts were unaffected and retained.

The matrix is finite: three valid pairs per workload. No run was repeated
because its speed or generated code was disappointing.

## Reproduction

`tools/benchmark_pr_workloads.py` takes a standard local model config, an engine
path, an arm label, workload, seed, token budget and output report path. Supply
the arm-specific engine arguments above in separate configs. Run one engine at
a time, alternating arms for seeds 123, 456 and 789, with `--tokens 2048` for
essay and `--tokens 3072` for agentic. Example:

```
python tools/benchmark_pr_workloads.py --config baseline.json --exe path/to/strata --arm baseline --workload essay --seed 123 --tokens 2048 --report essay-p1-baseline.json
```

Local configs and complete raw reports are in the integration worktree's
`docs/evidence/pr-workloads`. The submission branch includes the portable
driver and compact results; personal launcher/configuration files are excluded.
