# دليل المساهمة في Strata — النسخة العربية

هذا الدليل ترجمة وتفصيل عملي لـ [CONTRIBUTING.md](../../.github/CONTRIBUTING.md) وقوالب GitHub والفحوص الآلية في المستودع. المرجع القانوني هو الملف الإنجليزي في `.github/`؛ عند أي خلاف يعتمد عليه. الهدف: أن تكون مساهمتنا **مقبولة، مفيدة، ومطابقة لكل شرط** من شروط المشروع.

> **القاعدة الذهبية:** المساعدة بالذكاء الاصطناعي — بما فيها الوكلاء المساعدون — مرحّب بها، لكن **المساهم مسؤول عن فهم كل سطر غيّره، وعن تقديم دليل حقيقي، وعن الإجابة على أسئلة المراجعة**. لا تُرسل قياسات أو سجلات أو نتائج اختبار لم تُنتجها فعلاً.

## 1. قبل أن تبدأ

1. **ابحث أولاً** في [Issues](https://github.com/Niko1221/Strata/issues) و[Pull requests](https://github.com/Niko1221/Strata/pulls)، **بما في ذلك المغلقة**. إن كان نقاش قائم يغطي فكرتك، أضف إليه أدلة جديدة بدل فتح موضوع مكرّر.
2. **اقرأ** [AGENTS.md](../../AGENTS.md) ووثائق المكوّن الذي تريد تغييره (`docs/INSTALL.md`, `docs/TERMINAL_LAUNCH.md`, `docs/DETAILS.md`, `app/host/README.md`, ...).
3. **اتفق على النطاق في Issue قبل** أي ميزة كبيرة، أو إعادة هيكلة، أو تغيير بنية، أو تغيير افتراضي (`default`). اشرح: مشكلة المستخدم، السلوك المقترح، والمقايضات. **الاتفاق على النطاق لا يضمن الدمج**. الإصلاحات المركّزة وتقارير القياسات يمكن أن تذهب مباشرة إلى PR.
4. **مشكلة واحدة لكل PR**. حدّث نفس PR بعد الملاحظات؛ لا تفتح محاولات متنافسة لنفس التغيير.
5. **لا تُعيد تقديم مقترح رُفض** بعنوان آخر أو عبر وكيل آخر. إن ظهر دليل جديد، أعد الأمر إلى النقاش الأصلي واترك لـ maintainer قرار إعادة الفتح.

## 2. المناطق (Areas) وعنوان كل Issue وPR

كل عنوان يبدأ بمنطقة بين قوسين مربعين، ثم وصف قصير. القائمة مغلقة ولا يقبل غيرها:

| البادئة | تُستخدم لـ |
| --- | --- |
| `[Engine]` | المحرّك، النوى (kernels)، النماذج، الخادم وAPI |
| `[GUI]` | تطبيق سطح المكتب |
| `[TUI]` | الطرفية: `strata launch` و`connect` والمراقبة |
| `[Benchmark]` | القياسات والتقارير |
| `[Docs]` | الوثائق |
| `[Other]` | كل ما لا يناسب ما سبق، بما فيه التثبيت |

**الشكل المطلوب حرفياً** (يُفحص بـ workflow اسمه `Title area`، ويرفض العنوان إن لم يطابق):

```text
[Area] وصف قصير
```

أمثلة صحيحة: `[Engine] fix decode stop on long prompts` · `[GUI] keep the model list after a tab switch` · `[Docs] Add Arabic README and installation guide` · `[TUI] Add Arabic language and RTL support to the Terminal web page`.

> تنبيه تقني: الفاحص يستخدم النمط `^\[(Engine|GUI|TUI|Benchmark|Docs|Other)\] \S` — أي أنه يطلب **مسافة بعد القوس** ثم حرفاً غير فراغ. `[Docs]Add Arabic...` مرفوض.

## 3. فحوص الاستقبال (Intake) وإعادة الفتح

- بوت `Intake` يفحص كل Issue وPR جديد: إن لم يستوفِ الشكل، يضع وسم `needs-format` ويترك تعليقاً واحداً يشرح الناقص.
- إن بقي الوسم **5 أيام** يُغلق العنوان تلقائياً (`sweep`) مع تنبيه أن هذا تنظيف لا رفض.
- للإعادة: أصلح العنوان والوصف ثم اكتب `/reopen` في تعليق. فحص `reopen.yml` يعيد العنوان إن استوفى الشكل، ويقول ما ينقص إن لم يستوفِ. **وعند إعادة فتح عنوان أُغلق سابقاً يلزم اختبار جديد على إصدار 0.2.x وذكر المراجعة المُختبرة في قسم Validation** (رسالة البوت ما زالت تقول `0.2.0-beta` وهي قديمة؛ الإصدار الحالي 0.2.22).
- **لا تُرسل PR بقالب فارغ أو بعناصر placeholder**؛ البوت يقرأ الوصف ويتجاهل تعليقات HTML `<!-- -->`، ويعتبر قيمًا مثل `_no response_` و`none` و`n/a` و`todo` و`tbd` حقولاً فارغة، ويقيس **الطول الأدنى** لا المعنى.

## 4. متطلبات كل Issue

استخدم [نموذج Issue المناسب](https://github.com/Niko1221/Strata/issues/new/choose). الفاحص الآلي (`item-check.js`) يطلب حقولاً محددة بأقل طول للنص الحقيقي:

| النوع | الحقول الإلزامية (حدّ الأدنى) |
| --- | --- |
| Bug report | Area · Desktop app, Terminal or source? · What happened (20+) · Reproduction status · Strata version (3+) · Graphics card, memory and system (3+) |
| Feature request | Area · What do you want to do? (20+) — اشرح حاجة المستخدم والبديل الحالي |
| Question | Area · Your question (15+) — قل ما جرّبته وأين توقفت |
| Benchmark | What did you measure… (30+) · Reproduction status · ذكر إصدار Strata في المتن |

لنص حرّ (بدون نموذج): **80 حرفاً** على الأقل (40 للتصنيف enhancement/question)، ويجب أن يحتوي **إصدار Strata** (**GPU/VRAM/RAM/النظام**) في المتن.

هيكل تقرير الخطأ الموصى به (`Placeholders` تُستبدل بملاحظات حقيقية):

```text
Problem: <سلوك واحد لوحظ>
Environment: <commit, OS, GPU/VRAM, model/quant, relevant settings>
Reproduce: <أمر أو خطوات قصيرة>
Expected: <السلوك الموثّق أو المتوقع>
Actual: <ما لوحظ بالضبط والخطأ>
Evidence: <سجل منظّف من الأسرار>
Reproduction status: <reproduced locally OR unconfirmed static analysis>
```

**قواعد الصدق:** لا تخترع خطوات إعادة إنتاج ولا أخطاء ولا عتاداً ولا درجة خطورة. إن لم تستطع إعادة الإنتاج، قل ما فحصته وما الذي قد يتحقق من الفرضية. أي استنتاج من قراءة الكود أو من ماسح يُوسم **`unconfirmed static analysis`** ولا يُعرض كفشل لوحظ.

## 5. هيكل PR إلزامي

قالب [pull_request_template.md](../../.github/pull_request_template.md) يطلب الأقسام التالية، والفاحص يطلب `Problem and result` و`Validation` بـ **20 حرفاً على الأقل** لكلٍّ منهما:

```text
Problem and result: <ما الذي استدعى التغيير؛ السلوك قبل وبعد>
Related discussion: <رابط Issue وموافقة النطاق إن وُجدت؛ وإلا none>
Approach: <لماذا هذا الحل؛ أثر التوافق>
Validation:
  Passed: <أمر دقيق، المراجعة/البيئة، النتيجة المرصودة، سجل>
  Failed: <الأمر والفشل، أو none observed>
  Not run: <الفحص، السبب، ما بقي غير متحقق>
Limits: <القيود المعروفة أو العمل المتبقي>
```

قواعد محتوى PR:

- ابدأ بالمشكلة والنتيجة، **لا** بسرد ملفات ولا بملخّص diff مولّد آلياً.
- استبعد التنسيق العشوائي والتنظيف غير ذي الصلة وتغيير التبعيات والتجريدات التخمينية.
- أضف وثائق عندما يتغيّر ما يحتاج المستخدم أو المطوّر معرفته؛ تجنّب التكرار والخرائط التخمينية والوثائق المولّدة بلا معلومة قابلة للتنفيذ.
- حافظ على السلوك خارج نطاق التغيير؛ الميزات الجديدة **opt-in** والمسار الافتراضي يبقى مطابقاً للإصدار السابق ([AGENTS.md](../../AGENTS.md)).
- اقرأ الـ diff الكامل قبل الإرسال، بما فيه الملفات المولّدة؛ احذف مخرجات التنقيب والأسرار والمسارات الخاصة والملفات العارضة.
- فضّل فحص انحدار صغير ذي صلة على اختبارات تُعيد صياغة التنفيذ فقط، و**افحص الأمثلة** مقابل أوامر المشروع الفعلية.

## 6. التحقق (Validation) — القواعد الصارمة

- اذكر **الأوامر الدقيقة**، والمراجعة والبيئة التي اختُبرت، والنتيجة المرصودة، **وأرفق المخرجات أو سجلاً بها**. وابقِ **Passed** / **Failed** / **Not run** منفصلة دائماً.
- الأمر الذي تقترح تشغيله **ليس** دليلاً على أنه نجح. وCI على مراجعة أخرى ليس تحققاً من الكود الذي أرسلته.
- ابنِ كل backend يلمسه تغيير الكود: **CUDA وHIP وSYCL** حيث ينطبق، قبل طلب المراجعة.
- التنفيذ على العتاد يُذكر **منفصلاً** عن التجميع. الـ mock والفحص الساكن والبناء الناجح لا يثبتان صحة العتاد.
- إن افتقدت بيئة مطلوبة: أبقِ PR مسودة (`draft`)، اذكر الفحوص الناقصة، واطلب مساعدة محدّدة في نفس النقاش. **لا تدّعِ توافقاً لم تختبره**.
- ادعاءات الأداء تحتاج تشغيلاً قبل/بعد على **نفس العتاد ونفس الحمل** مع تحديد كل إعداد تغيّر، والحفاظ على التشغيلات والفشل والتباين. اتبع [دليل القياس المجتمعي](../COMMUNITY_BENCHMARKS.md)؛ بروتوكول [BENCHMARK_PROTOCOL.md](../BENCHMARK_PROTOCOL.md) لا يزال مسودة، **ولكن الطلبات المُعيَّرة ستستخدمه بمجرد تفعيله**. تشغيل سريع واحد لا يبرّر تغيير افتراضي ولا ادعاء سرعة لأجهزة أخرى.

### أوامر التحقق المستخدمة في مساهمتنا العربية

هذه أوامر محلية أجريناها بأنفسنا؛ وأي نتيجة تُذكر في وصف PR يجب أن تكون مخرجاتٍ حقيقية من تشغيلك أنت، لا نقلًا عن هذا الجدول.

```sh
# من جذر المستودع
python -W ignore tools/test_check_links.py
python tools/check --only docs

# من terminal/
python tools/web_i18n.py
python -m pytest serve/test_web_i18n.py serve/test_web_pictures_off.py serve/test_web_header_brand.py -q
python -m pytest tests/terminal/test_tui2_023_versions.py -q
python -m pytest tests/terminal/test_cli_arabic.py -q

# من app/host/ (عند تعريب تطبيق سطح المكتب)
npm test
node --test tests/languages-and-catalog.test.mjs
node --test tests/rtl-send-arrow.test.mjs
```

## 7. قواعد العمل بمساعدة الذكاء الاصطناعي

- استخدم الوكلاء للبحث والتنفيذ والشرح **بشرط أن تتمكن من مراجعة** عملهم.
- تحقق من ادعاءاتهم مقابل المصدر أو مخرجات الأوامر الفعلية أو مرجع أولي مُستشهد به.
- **لا تُرسل** قياسات مختلقة ولا نتائج اختبار مزعومة ولا سجلات مقلّدة ولا أقوالاً منقولة لم تتحقق منها.
- لا تحوّل فحص المستودع إلى دفعة Issues أو PRs تخمينية؛ جمّع النتائج ذات الصلة وأثّرها ثم أرسل الدليل المفيد.
- لا تعتبر ثقة وكيل أو موافقة نموذج آخر تحققاً. اجعل ردود المراجعة قصيرة ومباشرة، **وعالج التغيير أو الدليل المطلوب مباشرة**.
- يجوز لـ maintainer طلب تغيير أصغر، أو إعادة PR إلى مسودة، أو إغلاقه لغياب الدليل أو التكرار أو تجاهل النطاق المتفق عليه. مساهمة صغيرة بحدود صادقة أسهل مراجعة.

## 8. تقارير القياسات (Benchmarks)

PR النتائج فقط يحتوي: تقرير المستخدم، القياسات الخام، الإعداد المُنظّف، والسجلات الداعمة. يُبقى منفصلاً عن تغييرات المحرّك ويشمل النتائج السيئة والطلبات الفاشلة. لا تُستخدم أرقام من إصدار قديم كأنها للإصدار الحالي؛ كل رقم يُوسم بالعتاد والنموذج والتكميم وإصدار المحرّك والحمل (صيغة `Measured on:`).

## 9. الأمان والإفصاح

الثغرات التي يجب ألا تُنشر قبل الإصلاح تُبلّغ **خاصة** عبر تبويب Security → Report a vulnerability في GitHub ([رابط مباشر](https://github.com/Niko1221/Strata/security/advisories/new)). اذكر ما وجدت، وكيف يُعاد إنتاجه، وما الذي يحصل عليه المهاجم. أفكار التقوية العامة الآمنة للنشر تُقبل كـ Issue أو PR عادي، **وتُجمَع نتائج التدقيق في القضية [#544](https://github.com/Niko1221/Strata/issues/544)**. الإصدار المدعوم هو الأحدث، والإصلاحات تذهب إلى الإصدار التالي لا إلى القديم. راجع [SECURITY.md](../../.github/SECURITY.md).

## 10. قواعد كتابة الوثائق

- خطوات التثبيت في [INSTALL.md](../INSTALL.md)، وخطوات المصدر في [SOURCE_INSTALL.md](../SOURCE_INSTALL.md)، وتبقى READMEs العامة قصيرة.
- تحقق من الأمثلة مقابل محلّل الأوامر ومن أسماء الملفات مقابل أصول الإصدار.
- الصفحة تصف **الإصدار الحالي**؛ التاريخ والإصدارات القديمة والإعدادات المستبدلة تذهب إلى قسم `History / older measurements` في نهاية الصفحة أو إلى `docs/bench-results/` أو ملاحظات الإصدار. لا تُخلط في التعليمات.
- شكل كل صفحة دليل: العنوان → الغرض (1–3 أسطر) → بداية سريعة أو خطوات → أقسام `##` وجداول للخيارات → قسم تاريخ اختياري.
- كل رقم يُوسم مباشرة فوقه: `Measured on: hardware (GPU, CPU, RAM), model or set, Strata version, workload`.
- الترجمات الحالية في `docs/lang/` تتبع نمط `README.<lang>.md`. صفحة التثبيت العربية أُضيفت باسم `INSTALL.ar.md` بنفس النمط، مع إبقاء الروابط إلى الصفحات غير المترجمة بالإنجليزية وتوضيح ذلك صراحةً.
- الترجمات تحتاج فحص الروابط **والأمثلة** والمراسيات والاتساق فقط؛ **لا تحتاج بناء GPU**. (CI يعمل فعلياً عبر `docs.yml` ويستخدم `tools/check_links.py`؛ ويمكنك أنت تشغيل `tools/test_check_links.py` أيضاً.)

## 11. خريطة مساهمتنا إلى هذه القواعد

> **تنبيه:** هذا القسم **قرار داخلي لفريقنا** لتنظيم عملنا، وليس نصاً من `.github/CONTRIBUTING.md`. الأرقام أدناه مقيسة محلياً على نسخة العمل هذه، ويجب إعادة التحقق منها عند كل تحديث إصدار. المرجع الرسمي للقبول يبقى الملف الإنجليزي.

| المساهمة | البادئة | نطاق عملنا | التحقق المطلوب قبل أي رفع |
| --- | --- | --- | --- |
| README عربي + دليل تثبيت عربي + روابط اللغات | `[Docs]` | ترجمة وثائق فقط، بلا تغيير سلوك | `tools/test_check_links.py` + اختبار اتساق الإصدارات |
| إضافة العربية لواجهة Terminal مع RTL | `[TUI]` | 257 مفتاحاً + سطر اللغة وRTL | `web_i18n.py` + 3 ملفات اختبار ويب |
| إضافة العربية لتطبيق سطح المكتب | `[GUI]` | 4,075 مفتاحاً + عشرات الاختبارات + قرار RTL | `npm test` كاملاً + فحص المفاتيح والعناصر النائبة |
| مقال/فيديو عربي | `[Docs]` | محتوى خارج المستودع حتى يُنشر، ثم يُطلب ربطه | مراجعة `docs/MEDIA_KIT.md`، بلا ادعاءات سرعة غير مقيسة |

> **لا يُرفع أي تغيير قبل الانتهاء النهائي من التنفيذ والاختبار والتجربة الكاملة.** هذه قاعدة داخلية اعتمدناها نحن، وهي **أشد** من قواعد المشروع، وتُطبّق على كل المساهمات أعلاه بلا استثناء.
