# RX 6600M (gfx1032, 8 GiB): build the Windows HIP engine and run a model

The RX 6600M is the laptop RDNA2 card: `gfx1032`, wave32, 14 multiprocessors, 8 GiB of VRAM. Strata has no
ready-made engine package for it, but the HIP backend builds from source and runs a model on the card through
the same path as the other Radeon cards ([AMD_HIP.md](AMD_HIP.md)).

**Status: community report.** Every number on this page comes from one machine and was written by the card's
owner. The maintainers have not run an RX 6600M. Because no package exists, the Terminal and the app do not
offer this card; use a source checkout.

## 1. Build the engine

You need the card's driver (AMD Software: Adrenalin Edition), Visual Studio 2022 Build Tools with the C++
workload (the linker, the C runtime and the Windows SDK), Python and git. No admin rights are needed: ROCm
comes from AMD's TheRock Python wheels.

The documented path is the repository's Windows build script with one architecture:

```bat
set STRATA_HIP_ARCHS=gfx1032
tools\hip\build_windows.bat
```

The script installs `rocm[libraries,devel,device-gfx1032]` into `.rocm-win`, builds and writes
`dist\strata-windows-x64-hip.zip`. Its first step reads the ROCm root from `rocm-sdk.exe path --root`; on this
machine that console script printed nothing and exited with code 1. The script now falls back to the module
behind it (`python -m rocm_sdk path --root`), so it builds here as it is. An earlier run of this report went
through the four steps below instead; they are the script's own steps with the root read through the module,
and they stay here for a machine whose build stops at `ROCm has no compiler`.

```bat
rem 1. the ROCm root: compiler, HIP runtime, hipBLAS/rocBLAS, the gfx1032 device package
set "ROCM_VENV=<a venv with rocm[libraries,devel,device-gfx1032]>"
for /f "usebackq delims=" %%R in (`"%ROCM_VENV%\Scripts\python.exe" -m rocm_sdk path --root`) do set "ROCM=%%R"
set "ROCM_F=%ROCM:\=/%"

rem 2. MSVC: the linker, the CRT and the Windows SDK (clang compiles the host code too: CMake refuses to mix
rem    cl.exe with Clang for HIP)
call "%ProgramFiles(x86)%\Microsoft Visual Studio\Installer\vswhere.exe" -latest -products * -requires Microsoft.VisualStudio.Component.VC.Tools.x86.x64 -property installationPath > "%TEMP%\vs.txt"
set /p VS=<"%TEMP%\vs.txt"
call "%VS%\VC\Auxiliary\Build\vcvars64.bat"
set "PATH=%ROCM%\bin;%ROCM%\lib\llvm\bin;%PATH%"

rem 3. configure and build
cmake -G Ninja -S . -B build-hip-gfx1032 -DCMAKE_BUILD_TYPE=Release ^
  -DSTRATA_ENABLE_HIP=ON -DSTRATA_ENABLE_CUDA=OFF -DSTRATA_BUILD_TESTS=OFF -DSTRATA_PREFILL_MMQ=ON ^
  -DSTRATA_NATIVE_EXPERTS=ON -DSTRATA_PORTABLE=ON -DCMAKE_HIP_ARCHITECTURES=gfx1032 ^
  "-DCMAKE_C_COMPILER=%ROCM_F%/lib/llvm/bin/clang.exe" "-DCMAKE_CXX_COMPILER=%ROCM_F%/lib/llvm/bin/clang++.exe" ^
  "-DCMAKE_HIP_COMPILER=%ROCM_F%/lib/llvm/bin/clang++.exe" "-DCMAKE_HIP_COMPILER_ROCM_ROOT=%ROCM_F%" ^
  "-DCMAKE_PREFIX_PATH=%ROCM_F%" "-DCMAKE_HIP_FLAGS=--rocm-path=%ROCM_F% --rocm-device-lib-path=%ROCM_F%/lib/llvm/amdgcn/bitcode"
cmake --build build-hip-gfx1032 --target strata strata-device
```

One architecture only: the binary carries gfx1032 code and, like every one-arch build, stops on another card
with a message that names the card's architecture.

> **Measured on:** RX 6600M, 8 GiB (gfx1032), i5-13600, 95.7 GB RAM, Windows 10.0.26100, Visual Studio 2022
> Build Tools, ROCm 10.2.0a20260930 (TheRock wheels), engine 0.1.53 built from commit `46c152a1`.

| Result | Value |
| --- | --- |
| Build | 0 errors, 3,450 warnings, exit code 0 |
| Programs | `build-hip-gfx1032\strata.exe` (37 MB), `strata-device.exe` |

## 3. Run a model

The engine reads a pack. A native (IQ) pack keeps the experts in the source GGUF and reads them by offset, so
it needs the shard path too. The model used here is Qwen3.8-Flash-Next GSQ-RCO IQ1_M, two shards, 48 layers,
256 experts per layer (the pruned coder variant).

| Flag | Meaning on this card |
| --- | --- |
| `--pack DIR` | the pack directory (`tools/iq_pack.py` writes it) |
| `--native SHARD1` | the model's first shard; every other shard is found beside it by name |
| `--ple-gguf PATH` | shard that holds the PLE table; default: found by name beside `--native` |
| `--spec 4` | the speculative verify window; a native pack requires 2 or more |
| `--prefill auto` | prompt chunks; a native pack requires a chunk size |
| `--expert-profile P` | the ranked expert table that fills the VRAM cache at start |
| `--expert-cache auto` | as many expert slots as fit; with a profile, ranked by routing frequency |
| `--max-context 2048` | KV/state capacity for this test |
| `--max-new 16` | tokens to generate |
| `--stop-eos` | stop at the end-of-turn token (off by default; without it the run repeats) |

A missing flag is refused at start with exit code 2 and a message that names it. The one that is easy to miss
is `--expert-profile`: `--spec` needs the device residency table, and the token graph that builds it is created
only when a profile path is given. `--expert-cache N` alone is not enough.

```bat
build-hip-gfx1032\strata.exe --pack <pack> ^
  --native <model>-00001-of-00002.gguf ^
  --spec 4 --prefill auto --expert-profile data\expert-profile-coder.bin ^
  --expert-cache auto --stop-eos ^
  --tokens "760,6511,314,9338,369" --max-new 16 --max-context 2048
```

`data\expert-profile-coder.bin` is the 256-expert coder profile and matches this pack;
`data\expert-profile.bin` is the 512-expert one. Use the profile that matches your model.

Build the pack from the model's first shard with `tools/iq_pack.py --gguf <shard1> --out <pack>`
([MODELS.md](MODELS.md) names the model files).

`--tokens` takes ids. To turn text into ids, use the pack's tokenizer and pass the result, or write the ids
into a file and pass `--tokens-file`:

```python
from tools.strata_tokenizer import Tokenizer

ids = Tokenizer.from_gguf("<model>-00001-of-00002.gguf").encode("The capital of France is")
print(",".join(map(str, ids)))   # 760,6511,314,9338,369
```

## 4. Setup and the server

`setup.py` (or `START-HERE.bat`) installs the card from a source checkout. gfx1032 is an experimental opt-in
and no release zip carries its code, so pass the switch and the zip built in section 1:

```bat
set STRATA_EXPERIMENTAL_GFX1032=1
START-HERE.bat --backend hip --prebuilt dist --family coder --model IQ1_M ^
  --gguf-dir <the folder with the two shards> --data-dir <the data folder> ^
  --context 8192 --yes --no-start
```

**`--context 8192` on this card.** Left to itself, setup recommends 32K tokens for a card under 14 GiB, and at
32K the engine stops: the expert cache needs 672 MiB (its 265-slot minimum) and this 8 GiB card is 342 MiB
short once the KV cache, the dense weights and the draft head are in. At 8K the same settings fill 121 to 337
experts. Setup also needs llama.cpp's source zip (it fetches it from GitHub in step 4, for `gguf-py`); on a PC
that cannot reach GitHub, put the pinned source into `third_party\llama.cpp` first.

After that first run the card needs no switch: `SETUP.bat` (change settings, install another model) and
`START-HERE.bat` use the engine already in `engine\`, and `START-HERE.bat` starts the saved
`strata-<model>.json`.

> **Measured on:** the machine of this report, engine 0.1.53 built from commit `46c152a1`, zip built with
> `tools/hip/package_windows.py` (125 MiB, 386 MiB unpacked, archs gfx1032, ROCm 10.2.0a20260930),
> Qwen3.8-Flash-Next GSQ-RCO IQ1_M coder pack.

| Step | Result |
| --- | --- |
| Setup, `--context 8192` | engine 0.1.53 installed from the local zip, pack and MTP draft reused, `run-coder-iq1_m.bat` written |
| Engine at 32K context | exit code 1: `no VRAM is left for the expert cache ... about 342 MiB more than this card has free` (Windows budgeted 6,409 of 8,176 MiB for the process) |
| Engine at 8K context | session up, 121 experts (0.23 GiB) on one start, 337 (0.65 GiB) on the next, filled from the coder profile |
| Server request, 160 new tokens | 19.3 s wall over HTTP (`/v1/chat/completions`), answer complete |
| Server timings, short answer | 10.5 and 17.5 predicted tok/s with the MTP draft (9 of 12, 25 of 35 draft tokens accepted) |

The server reported `0 MiB of VRAM free with everything loaded` and named `--vram-reserve-mib` as the cure for
stalls; the requests above did not stall. The zip carries no picture reader, so setup switched images off.

## 5. The Terminal (`strata launch`)

`strata launch` starts the engine package it finds in the Terminal's component folder
(`strata_control/engine_component.py`); it never downloads one. The update feed has no engine for this card
(its Windows RDNA2 package carries gfx1030 and gfx1031), so make one from the engine folder setup installed:

```bat
python packaging\package_engine.py --src engine --backend hip --version 0.1.53 ^
  --out "%LOCALAPPDATA%\Strata\components\engine" --arch gfx1032 --variant rdna2 --tree
```

`0.1.53` is this report's engine version (`engine\BUILD.json`); use yours.
That writes `0.1.53-windows-x86_64-hip-rdna2` (385.9 MiB, 175 files) into the per-user component folder. When
that folder is on another drive (here `C:` was full), start the Terminal with `STRATA_COMPONENTS_DIR` set to
the folder that holds it.

One command serves the model, with or without a run config:

```bat
set STRATA_COMPONENTS_DIR=<the folder holding components\engine>
strata launch --family coder --model IQ1_M --model-path <the folder with the .gguf files> ^
  --data-dir <the data folder> --context 8k --vision off --tune skip --access local --port 8081 ^
  --no-tui --yes
```

(`--port 8081`: the server setup started had 8080. `--plan` in place of the start prints what would happen; with
`--model-path` it reads `download  Nothing to download: your model files are used where they are.`)

**`--model-path` is what keeps this offline.** Given the `.gguf` files, the Terminal runs setup itself with
those files: the model step prints `The model files are on this computer; checking them`, then it prepares the
pack once and saves the settings. Without `--model-path` the Terminal looks in its data folder
(`models\coder-IQ1_M`), counts the whole model as missing when that is empty (some 58 GB for this pack), and
stops at the disk check. After the first run, the saved `strata-coder-iq1_m.json` matches the same family,
model, context and vision choices, so the next launch skips setup: `coder IQ1_M is already installed with
these choices.`

- **`--context 8k` is required here.** Left to itself the Terminal recommends 32K for a card under 14 GiB, and
  at 32K the engine stops (section 4). The context is also part of "the model is already installed with these
  choices": 32K counts as a different choice, and the Terminal then tries to install the model again.
- **`--vision off`** because the coder zip carries no picture reader; the Terminal would fetch 0.9 GB of it.
- The Terminal needs the packages in `requirements.txt` (the server uses `jinja2`). A source checkout started
  with a Python that has none of them stops with `No module named 'jinja2'`; this machine ran the repo's
  `.venv`.
- `strata launch --status` shows what is serving; `strata launch --stop` stops it.

> **Measured on:** the machine of this report, engine 0.1.53 built from commit `46c152a1`, the component
> package above, ROCm 10.2.0a20260930, Qwen3.8-Flash-Next GSQ-RCO IQ1_M coder pack, context 8192, greedy
> sampling, `--expert-cache auto` with the coder profile.

| Step | Result |
| --- | --- |
| Engine check | `Engine 0.1.53 (hip) is installed.` (from the component package) |
| Model | `coder IQ1_M is already installed with these choices.` (setup's `strata-coder-iq1_m.json`) |
| Load | `The model is loaded and answering`; 23.42 GiB paged in at 1.98 GiB/s |
| Ready | `http://127.0.0.1:8081`; `strata launch --status` prints `iq1_m-8k: ready at http://127.0.0.1:8081` |
| Request 1, `max_tokens` 32 | 61 prompt tokens at 15.2 tok/s, 32 new at 7.5 tok/s (MTP draft 22 of 31 accepted), 8.3 s wall; stopped by the token limit, reasoning only |
| Request 2, `max_tokens` 96 | 56 prompt tokens cached, 5 read at 12.7 tok/s, 53 new at 8.6 tok/s (37 of 44), 6.6 s wall; answered `The capital of France is Paris.` |
| VRAM | 134 expert slots (0.26 GiB); the engine warned `0 MiB of VRAM free with everything loaded` (requests did not stall) |
| Decode expert cache | 0.7 to 6.1% hits over the three requests; 10.6% of all routed experts were read by the GPU over PCIe, the other misses computed by the CPU pool |

The rows above reuse a run config setup had written. The same command with `--model-path` and no run config
at all was run too, and it is the one that matters for a machine that never ran setup: the Terminal ran setup
by itself (`Getting the model files` / `The model files are on this computer; checking them` / `Preparing your
model for Strata (one time)` / `Preparing the draft layer` / `Saving the model's settings`) and was serving in
46 s from that command (the model load had printed `Loading the model… 30 s` just before ready). No download
step appeared. The engine was the component package
(`...\components\engine\0.1.53-windows-x86_64-hip-rdna2\strata.exe` in its log), and one request returned
`The capital of France is Paris.` (63 prompt, 41 new tokens, 8.5 s wall).

## 6. Speed on this card

> **Measured on:** RX 6600M, 8 GiB (gfx1032), i5-13600 (no AVX-512), 95.7 GB RAM, Windows 10.0.26100,
> ROCm 10.2.0a20260930, engine 0.1.53 from commit `46c152a1`, Qwen3.8-Flash-Next GSQ-RCO IQ1_M coder pack
> (256 experts, 48 layers), 2,048-cell context, greedy sampling, `--expert-cache auto` with the coder profile.

| Workload | Result |
| --- | --- |
| Decode, 16 tokens, prompt `The capital of France is` | 5.70 tok/s (2,806 ms) |
| Decode, 24 tokens, one-line question, `STRATA_HIP_PROMPT_F16=1` | 5.98 tok/s (4,016 ms) |
| Expert cache | 1,165 slots, 2.25 GiB, pre-filled from the profile in 0.7 s |
| CPU pool | 9 workers |
| PCIe probe (host to device) | 6.5 GB/s |

Both runs were made without `--stop-eos`. Run 1 answered
` Paris. The capital of Germany is Berlin. The capital of Italy is Rome.` Run 2 answered `11, 13, 17` and,
without `--stop-eos`, generated the same words again. Both runs exited with code 0.

What the output is and is not:

- **The decode rate is the expert path's, not the GPU kernels'.** At 8 GiB the card holds 1,165 of the
  model's 12,288 (layer, expert) pairs, so most routed experts are streamed over PCIe and computed by the CPU
  pool. The per-round report of run 2 reads `wait for rings 116.902 pool 85.231 ... ms/round` against a 223 ms
  round (4,016 ms over 18 rounds). A bigger cache needs more than 8 GiB of VRAM; a faster CPU and PCIe are
  what move this number.
- **Do not read the first prefill as prompt speed.** The first prompt of a run also captures the verify
  windows and loads the modules: 15.6 s for 4 prompt tokens in run 1 and 17.2 s for 16 prompt tokens in run 2.
  A steady prompt rate needs a second, longer prompt on the same run, which this report did not measure.
- `STRATA_HIP_PROMPT_F16=1` is the tip the engine prints on gfx103x (FP16 prompt GEMMs; rocBLAS has tuned FP16
  kernels for this family, see [AMD_HIP.md](AMD_HIP.md#rdna2-gfx1030)). It was set on run 2 only.
- **A longer run decodes more slowly.** Over 64 tokens the same build, prompt and settings measure 4.0-4.2 tok/s:
  the average round grows from about 187 ms to about 280 ms as the run goes on. The worker-count sweep behind
  this number is in the
  [Windows workers benchmark](benchmarks/windows-zen2-gfx1030-workers.md#one-processor-group-with-streamed-experts-rx-6600m-gfx1032).
  There the CPU pool computed 9.6 distinct experts / 12.9 routings per layer per round, yet took about a fifth
  of a round (52 of about 275 ms), so its worker count is not what limits decode on this card.
- Experts computed in the VRAM cache round differently from the CPU path, so a reply can differ slightly from
  a run without the cache (same quality; `bench/results/2026-09-27-cache-parity`).

## 7. Limits and what was not tested

- **One card, one machine, Windows only.** Linux was not tried.
- **One model and one quantization** (Qwen3.8-Flash-Next GSQ-RCO IQ1_M, coder pack). Larger or denser models
  need more system RAM and a fast SSD for the PLE table, as on the other RDNA2 cards.
- **Not tested:** `--serve` on Linux, contexts above 8K through setup (see section 4: 32K does not fit),
  the picture readers (the zip here was built without them), multiple GPUs and the HIP unit tests (`tests`
  argument of `build_windows.bat`).
- **The Terminal's model install with no files at all was not run.** With `--model-path` the Terminal ran
  setup itself and downloaded nothing (section 5). Without it, setup counts the whole model as missing (about
  58 GB for this pack) and stops at the disk check: this machine's data drive had 2 GB free, so that download
  was never fetched. One earlier attempt with `--model-path` was stopped after three minutes on a step label
  that had not moved; its own log then showed setup had already printed `coder IQ1_M is ready.`, so the label
  lagged behind the work, not the other way round. The clean run of the same command took 46 s.
- **No hipBLASLt tuning table for gfx1032** was used. A hand build carries none, so the prompt GEMMs run
  without a table ([AMD_HIP.md](AMD_HIP.md) says a hand-built engine has none).
