# K16V8: FP16 keys, INT8 values

`--kv k16v8` stores the QSA cache as FP16 K and INT8 V (codes plus one FP16
scale per 64 values). It is a middle point between `--kv int8` (1,056 B/cell)
and `--kv fp16` (2,048 B/cell): **1,552 B/cell**. K keeps FP16 precision for the
attention scores, while V keeps the memory saving of INT8.

| KV | K storage | V storage | bytes/cell |
| --- | --- | --- | ---: |
| `fp16` | FP16 | FP16 | 2,048 |
| `k16v8` | FP16 | INT8 + scale/64 | 1,552 |
| `int8` | INT8 + scale/64 | INT8 + scale/64 | 1,056 |
| `k8v4` | INT8 + scale/64 | rotated Q4_0 | 816 |

The format streams with `--kv-resident` (three runs: FP16 K, V codes, V scales)
and works with the MTP drafter, which stays plain INT8 as it does under `k8v4`.
It is not rotated: `STRATA_KV_ROT` does not apply.

## Performance

Controlled A/B on the same engine, model and prompt: Qwen3.8-Flash-Next IQ3_S
on an RX 6800 (gfx1030), HIP, `STRATA_HIP_PROMPT_F16=1`, MTP spec 4, 13,109-token
prompt, fully resident KV (`--kv-resident 0`):

| KV | prefill tok/s | decode tok/s | bytes/cell |
| --- | ---: | ---: | ---: |
| `int8` | 919.2 | 32.15 | 1,056 |
| `k16v8` | 917.9 | 34.48 | 1,552 |
| `fp16` | 906.6 | 33.90 | 2,048 |

The three are within run-to-run and draft-acceptance noise on this workload.
K16V8 is effectively int8 speed with FP16 K, and 24% smaller than fp16.

At 96k context and 12 QSA layers the host copy is 1.71 GiB (vs ~1.16 GiB for
int8 and ~2.25 GiB for fp16); 32,768 resident cells use ~610 MB of VRAM
(vs ~415 MB int8 and ~805 MB fp16). The extra VRAM against int8 can reduce the
expert cache by roughly 200 MB.

## Output length on the same prompt

Prompt used for all three outputs:

> Make an animated SVG of an anthropomorphic cat holding a sword

| KV | output tokens |
| --- | ---: |
| `int8` | 37k |
| `k16v8` | 29k |
| `fp16` | 25k |

On this workload, higher KV precision correlated with fewer output tokens:
int8 produced the longest response, fp16 the shortest, and k16v8 sat between
them. That is consistent with less overthinking when the cache is more precise,
but it is a single observation, not a general quality or latency guarantee.

## Compatibility

Exercised on this branch:

- `--kv-resident 0` and `--kv-resident 32768` (streamed and resident)
- `--mtp` / `--spec 4`
- `--prompt-cache` prefix reuse
- `--max-context 98304`
- vision, control vectors, `--adapt-async`, `--expert-cache auto`
- HIP gfx1030

`--no-fast-attn` and `--native-flash-attn-short` fall back to the fused decode
attention for k16v8; the gather/native path is not implemented for this format.

Not yet exercised: `--batch`, `--layer-split`, `--pipeline-windows`, `--kv-grow`
(elastic), and a CUDA build. The batch slots/rows and elastic allocation paths
are implemented. On CUDA the prompt attention falls back to the decode kernel
instead of the tensor-core prompt kernel; gfx1030 already uses that path for
most formats.

`--cache-suffix-reuse` and `--kv-pool-tokens` are not part of `origin/main`, so
this change is independent of the SCR branch.
