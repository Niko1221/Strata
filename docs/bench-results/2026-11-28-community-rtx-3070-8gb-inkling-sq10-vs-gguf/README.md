# RTX 3070 8 GB — Inkling SQ-10 against GSQ-RCO IQ3_S and three community GGUFs
## Hardware
NVIDIA GeForce RTX 3070, 8 GiB (sm_86), Intel Core i7-9700KF, 63.92 GiB of usable RAM, Windows 11, CUDA 13.0, models on an NVMe drive. One request at a time; Chrome, Edge WebView, Adobe and the local desktop applications are closed before the runs, and the GPU idles at about 620 MiB.
## Versions and settings
App and Terminal 0.2.23, Control 0.1.70, `strata-inkling` 0.1.70 for every Inkling row, `strata-engine` 0.1.70 for the Qwen rows. All runs go through a local `serve/server.py` run config rather than `strata launch`, because the local scheduler keeps several models behind one port. Inkling rows use `--kv k8v4` and the native 262,144-token window. Qwen rows use `--mtp 2` at the 76,800-token context the launcher computes for this card: 262,144 is refused with `a context of 262144 tokens does not fit on this graphics card: its conversation memory needs 10.56 GiB and only 3.15 GiB is free after the model. Start it again with a shorter context (76800 tokens fit here)`. Every argument is in `results.json`.
## How it was measured
Four series of 256 new tokens on an 870-token prompt, then a 1,983-token prefill, one 18,953-token prompt carrying a needle, ten auto-graded quality probes (arithmetic, a logic trap, Python, a JSON schema, French prose, a needle, a tool call, an extraction, token counting, multiplication), one 768x512 image for the vision path, then prompt probes at about 30k and 60k tokens where the model allows it. Decode and prompt speeds are the engine's own `predicted_per_second` and `prompt_per_second`; the table shows medians of the four series and `results.json` lists every run. Loads alternate between models so a thermal or allocator drift does not land on one side only. No prompt cache is reused: #7336 reports that a branch re-prefills everything on this engine, and the unique prefix every prompt carries keeps these cold numbers.
This is not the standard protocol. `strata bench run` and `docs/BENCHMARK_PROTOCOL.md` were not used, so these are community numbers under `docs/COMMUNITY_BENCHMARKS.md`, in the same spirit as the reports that predate the protocol.

## What the numbers show
**On 8 GiB the native pack wins the short prompt and loses at depth.** `SQ-10` leads at 28-29 tok/s and by a wide margin in prompt speed (297 tok/s against 141-172), but at 18,953 tokens it falls to 10.1 tok/s where the community IQ3_S build holds 16.1. The difference is placement, not precision: SQ-10 keeps 2.91 GiB of experts on the card and pushes its whole KV into host memory as soon as about 400 MiB of VRAM are missing.
**The IQ3_S prompt gap is a kernel problem with a fix in flight, not a property of the format.** Our rows reproduce the effect at 8 GiB (172 and 141 tok/s against 297), and #7337 measures it on an RTX 3090 with `STRATA_INK_PROF=2`: 512 tok/s for `GSQ-RCO-IQ3_S.gguf` against 2,170 for `SQ-20.strata`, with 91.5 % of the time inside `gu(gguf)` and `dn(gguf)` and a 5x patch proposed. Read the prompt column of any IQ-family row as "current kernels".
**The Qwen3.6-35B pair isolates the value of the MTP block.** Ornith and HauhauCS are the same architecture at the same size (21.71 against 21.17 GB), both with all 256 experts per layer in pinned host memory and none in VRAM, both near 120-127 tok/s of prompt. Ornith loads the MTP block and accepts 99 of 144 draft tokens for 30.8 tok/s; HauhauCS logs `drafts accepted 0 of 0` and stays at 23.9. That 30 % spread comes from a quantization dropping the MTP head.
**Drafter on the same pack, 8 GiB, alternating loads:** `SQ-10` reaches 28.0 and 29.1 tok/s with DSpark against 26.1 without (4 series each), for 70 MiB of VRAM and an identical expert tier. Worth +6 to +10 % below roughly 3k tokens of context and nothing beyond, which is the opposite trade-off to DFlash 2 on a 24 GiB card, where the same engine refuses the drafter on our card with `DFlash 2 not loaded: it would move part of the model off the card (the experts need 8.0 GiB, 2.5 GiB fit with the drafter's 1255 MiB, 3.7 GiB without it)`.
## Failed requests and refusals
Two of the five community candidates never load, and they are reported because a benchmark that hides them is not usable:
- `huihui-ai/Huihui-Qwen3.6-35B-A3B-abliterated-MTP` `Q2_K` (13.25 GB) stops with `strata-q36: blk.0.attn_gate.weight is Q2_K, which the native MMVQ does not take`.
- `Tsunderee/Inkling-2-Mini-Bonsai-QAT-GGUF` `bonsai_6g1-step75` (6.65 GB, llama.cpp layout, `Q1_0`/`Q2_0` experts) exits with code 1 and writes only `open: Failed to open .strata file: …`. Both `Q1_0` and `Q2_0` appear in `strata-inkling` 0.1.70, so the tensor type is not obviously the blocker; reported separately as an issue.
One nuance on the AtomicChat row: the drafter stays off, but not because of the GGUF path. Control looks for `dflash2.safetensors` in the model's own directory, and this file lives in another folder, so it writes `--draft off` with no note. Copying the sidecar next to the GGUF gives `--draft dflash2`, as the `.strata` rows do.
## Limits
One machine, one pass of the suite, no agentic grid, no clock or power capture, no standard-protocol conformance. The Qwen rows are bound by pinned host memory rather than by the quant, so their speeds should not be extrapolated to a card with more VRAM. The reference rows for `SQ-10` and `GSQ-RCO-IQ3_S` were measured the same night with the same protocol, immediately before these three, so they are comparable but not a separate campaign.
