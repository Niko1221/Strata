为什么按尺寸分桶

归还什么尺寸，就接着复用什么尺寸

同一层内交换的两个专家块大小一致。按尺寸维护 spare 池，换入专家释放的块，正好能接住下一次同尺寸交换。

本次 IQ2_XS 有三种块大小

1,177,600 B约 1.123 MiB
… × n 个 spare
1,305,600 B约 1.245 MiB
… × n 个 spare
1,510,400 B约 1.440 MiB
… × n 个 spare

每个桶的物理块数量保持不变。权重进入不同物理块后，专家到 host/device 地址的映射随所有权一起更新。

每轮拿走一个 spare，
再归还一个同尺寸块。

原复制路径给每个交换缓冲分配最大块容量；分桶轮转为每种尺寸分别预留缓冲，以保证任何一层都有同尺寸 spare 可用。

关闭：n × max(块大小)
开启：n × sum(不同块大小)

展开：含异步 bounce 缓冲的一般公式

设不同专家块大小之和为 S，最大块为 L；总预留交换槽为 N，其中 b 个只用于 bounce 暂存。关闭轮转为 N × L；开启为 (N − b) × S + b × L。因此额外缓冲载荷 ΔM = (N − b) × (S − L)。

当前版本设 s = min(adapt-swaps, 96)。普通模式 N=s、b=0；异步模式 N=2s、b=s，二者因轮转增加的载荷都为 s × (S−L)。单一块大小时 S=L，额外载荷为 0。该公式未计少量所有权元数据和驱动映射开销。

本轮正式请求的轮转计数确认，合计避免了 19.87 GiB 主机 memcpy 载荷。收益大小与交换频率、块大小，以及复制是否落在解码关键路径上有关。

直接节省

CPU 复制与内存带宽

淘汰专家已经在 RAM 暂存缓冲中，提交阶段直接把它登记为常驻块。省去一次读取旧缓冲、写入新位置的 memcpy；GPU 与 RAM 之间的 H2D/D2H 继续执行。

资源代价

多约 227 MiB 锁页 RAM

本配置 spare 池从 138.281 增到 365.625 MiB。显存专家缓存仍为 13503 槽 / 18530 MiB，两端一致。Linux VmLck、RSS 单项不能覆盖全部 CUDA 锁页内存。

适用前提

完整锁页、可映射的 RAM 副本

官方开关要求 RAM 专家副本和交换缓冲可锁页、可映射到 GPU。其他布局走复制路径，日志说明启用结果。整个生命周期仍要维护容量、地址配对和读写完成顺序。

当前环境

官方 16 槽，存在 CPU 回退

四轮正式请求的 CPU 路径 routed entries 为 515 / 325 / 187 / 739。7 workers 和约 295 MiB 剩余显存触发了引擎调优提示；本轮保持两端设置一致，GPU paging 未测量。

权重文件、量化格式和计算 kernel 在两端相同；变化集中在交换缓冲的分配与提交。当前数据同时包含自由生成、CPU/GPU 分工和 MTP 的实际运行效果。后续隔离纯复制收益，需要进一步固定生成轨迹并核对数值路径。
