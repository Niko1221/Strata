# 数据库故障排查实战手册：从微观锁等待到宏观容量规划

## 第一章：锁等待与死锁——并发控制的“黑箱”解析

在数据库系统中，锁是保证数据一致性的基石，但也是引发性能瓶颈和系统挂起的最常见原因之一。当多个事务试图访问同一资源时，如果其中一个事务持有锁而另一个事务需要获取该锁，就会发生锁等待。如果两个或多个事务互相等待对方释放锁，则形成死锁。排查锁问题不仅仅是看“谁在等”，更要理解“为什么在等”以及“如何打破僵局”。

### 1.1 核心概念与隔离级别对锁的影响

首先必须明确，不同的数据库引擎（如 MySQL InnoDB, PostgreSQL, Oracle）和不同的事务隔离级别（Read Uncommitted, Read Committed, Repeatable Read, Serializable）决定了锁的类型和粒度。

*   **行级锁 vs 表级锁**：InnoDB 默认使用行级锁，但在某些情况下（如全表扫描或无索引更新）会升级为表级锁。MyISAM 则默认使用表级锁。
*   **意向锁（Intention Locks）**：这是 InnoDB 特有的机制。当一个事务在表中某一行上持有排他锁时，它会在表级别持有意向排他锁（IX）。这允许其他事务快速判断是否需要对整个表加锁，从而避免全表扫描检查每一行是否有锁。
*   **间隙锁（Gap Locks）与临键锁（Next-Key Locks）**：在 Repeatable Read 隔离级别下，InnoDB 不仅锁定记录本身，还锁定记录之间的间隙。这是为了防止幻读（Phantom Read）。例如，如果表中存在 ID=10 和 ID=20 的记录，事务 A 查询 `SELECT * FROM table WHERE id > 15 FOR UPDATE`，它会锁定 (10, 20) 这个区间。此时事务 B 试图插入 ID=15 的数据会被阻塞。这是很多“莫名其妙”的锁等待根源。
