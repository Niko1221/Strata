### 1. Incorrect ASS Color Alpha Channel
**Problem:** In `_ass_colour`, the alpha channel is inverted. In ASS format, `00` is opaque and `FF` is transparent. The code uses `0` for opaque (correct) but the docstring and logic imply standard alpha usage. More critically, `BackColour` uses `0x40` (64), which is semi-transparent, but `OutlineColour` uses `0x60` (96). However, the biggest bug is that `PrimaryColour` and `SecondaryColour` use `alpha=0` (opaque), which is correct, but `BackColour` (shadow) often needs to be semi-transparent. The real bug is that `&H` format expects `AABBGGRR`. The code produces `&H{alpha:02X}{c[4:6]}{c[2:4]}{c[0:2]}`. If `alpha=0`, it is `00`. This is correct for opaque. However, `BackColour` is set to `0x40` (64), which is quite transparent. The main issue is that `SecondaryColour` is often used for karaoke or secondary text, but here it's just set to accent. The critical bug is actually in `srt_to_ass`: it assumes `parse_srt` returns `lines` as a list of strings, but `parse_srt` returns `lines` as a list of strings *without* stripping trailing whitespace or handling multi-line cues correctly if the SRT has blank lines inside a cue (which `re.split(r"\n\s*\n")` handles, but `lines[head+1:]` might include empty strings if the block had trailing newlines).

Actually, the most severe bug is in `build_srt`: **`cues.sort(key=lambda c: c[0])` sorts by start time, but if two cues have the same start time, the order is undefined.
